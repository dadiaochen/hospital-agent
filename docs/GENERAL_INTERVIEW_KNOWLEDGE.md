## 1. Java 与 JVM

### Q1：Java 的内存区域有哪些？

**参考回答：**

运行时通常可以从程序计数器、虚拟机栈、本地方法栈、堆和方法区/元空间来理解。线程私有区域包括程序计数器、虚拟机栈和本地方法栈；堆和方法区通常由进程内线程共享。

对象一般在堆上分配，方法调用的局部变量和调用帧位于线程栈，类元数据位于元空间。具体实现和垃圾收集器会影响细节，回答时要区分 JVM 规范和某个具体 HotSpot 版本。

### Q2：Java 垃圾回收的基本思路是什么？

**参考回答：**

GC 通常通过可达性分析判断对象是否仍然被根对象引用，再配合分代回收、标记清除、复制和压缩等算法回收空间。分代假设大多数对象朝生夕死，因此年轻代和老年代可以使用不同策略。

排查 GC 问题时关注 GC 日志、暂停时间、堆使用曲线、对象分配速率和 heap dump，不要只看“内存占用高”就下结论。

### Q3：什么情况下会出现 Java 内存泄漏？

**参考回答：**

内存泄漏通常不是 GC 失效，而是对象仍被不应该存在的强引用持有。例如静态集合不断增长、监听器没有移除、ThreadLocal 没有清理、缓存没有上限、线程或连接没有释放。

排查可以结合 heap dump、引用链、GC 日志和监控曲线，先判断是泄漏、缓存增长、瞬时流量还是堆配置不足。

### Q4：HashMap 和 ConcurrentHashMap 有什么区别？

**参考回答：**

HashMap 不是线程安全的，并发读写可能产生数据不一致。ConcurrentHashMap 面向并发场景，通过更细粒度的并发控制降低锁竞争，读操作通常不需要锁住整个容器。

实际选择要看是否需要并发安全、是否允许 null、读写比例和一致性要求，不能只因为“并发”就无条件使用 ConcurrentHashMap。

## 2. 计算机网络

### Q5：TCP 和 UDP 有什么区别？

**参考回答：**

TCP 是面向连接、可靠、有序的字节流协议，通过序号、确认、重传、流量控制和拥塞控制提供可靠传输；UDP 是无连接的数据报协议，不保证到达、顺序和去重，但头部更简单、延迟更低、适合实时性和广播类场景。

可靠性不是 TCP 的全部成本，连接建立、状态维护、拥塞控制和重传都会增加开销。

### Q6：TCP 三次握手为什么需要三次？

**参考回答：**

三次握手需要让客户端和服务端都确认双方的发送和接收能力，并同步初始序列号。两次不足以让服务端确认客户端能收到自己的响应，三次可以避免历史连接请求造成错误状态。

### Q7：TCP 四次挥手为什么通常是四次？

**参考回答：**

TCP 是全双工连接，双方的发送方向需要分别关闭。主动关闭方发送 FIN 后，对端先 ACK，等数据发送完成后再发送自己的 FIN，主动关闭方再 ACK，因此通常需要四次报文。

### Q8：TCP 如何保证可靠传输？

**参考回答：**

主要依靠序号和确认号保证顺序与确认，通过超时重传、快速重传处理丢包，通过滑动窗口和流量控制避免接收方被压垮，通过拥塞控制根据网络情况调整发送速率。

### Q9：HTTP 和 HTTPS 有什么区别？

**参考回答：**

HTTPS 是 HTTP 加 TLS。TLS 通过证书验证服务端身份，并通过密钥协商建立加密通信，保证传输过程中的机密性和完整性。HTTPS 不能保证服务端业务逻辑一定可信，也不会自动解决应用层鉴权和越权问题。

### Q10：HTTP/1.1、HTTP/2、HTTP/3 有什么主要区别？

**参考回答：**

HTTP/1.1 主要基于 TCP，常见问题是连接复用和队头阻塞；HTTP/2 在同一连接上支持二进制分帧、多路复用和头部压缩；HTTP/3 基于 QUIC/UDP，目标是减少 TCP 建连和传输层队头阻塞对连接的影响。

回答时不需要背所有特性，但要能说明协议层次、连接复用和队头阻塞的变化。

### Q11：DNS 查询大致怎么做？

**参考回答：**

客户端通常先查浏览器、系统和本地缓存，未命中时向递归 DNS 查询。递归服务器可以继续向根、顶级域和权威 DNS 查询，最后返回域名对应的记录并按 TTL 缓存。

### Q12：select、poll 和 epoll 有什么区别？

**参考回答：**

select 和 poll 通常需要应用每次遍历关注的文件描述符，存在数量限制或遍历成本。epoll 由内核维护关注集合，事件发生时返回就绪描述符，更适合大量连接的 IO 多路复用。

它们解决的是 IO 事件等待问题，不等同于业务处理本身变成并行，也不意味着所有场景都应该使用 epoll。

## 3. 操作系统

### Q13：进程、线程和协程有什么区别？

**参考回答：**

进程拥有相对独立的地址空间和资源，隔离性强但切换和通信成本较高；线程共享进程资源，切换成本较低但需要处理并发安全；协程通常由用户态调度，适合在 IO 等待点主动让出执行权。

Python asyncio 适合 IO 密集型协作式并发，但不会自动让 CPU 密集型任务获得多核加速。

### Q14：什么是虚拟内存？

**参考回答：**

虚拟内存给每个进程提供独立、连续的地址空间，操作系统通过页表把虚拟地址映射到物理页，并可以利用缺页中断和磁盘交换扩展可用地址空间。

虚拟内存带来隔离和按需分配能力，但频繁缺页和 swap 会显著降低性能。

### Q15：死锁产生的必要条件有哪些？

**参考回答：**

通常包括互斥、占有且等待、不可剥夺和循环等待。预防可以破坏其中一个条件，例如统一加锁顺序、缩短持锁时间、设置超时或避免嵌套锁；检测则可以通过等待图和超时机制发现问题。

### Q16：阻塞 IO、非阻塞 IO 和 IO 多路复用有什么区别？

**参考回答：**

阻塞 IO 会让调用线程等待操作完成；非阻塞 IO 立即返回，由调用方再次检查；IO 多路复用允许一个线程等待多个文件描述符的就绪事件，再处理已准备好的连接。

IO 多路复用减少了等待线程数量，但业务处理仍然需要避免在事件循环中执行长时间 CPU 任务。

### Q17：用户态和内核态切换为什么有成本？

**参考回答：**

用户程序访问受保护资源时需要通过系统调用进入内核态，涉及权限检查、上下文保存和恢复等开销。频繁的小 IO、锁竞争和系统调用可能影响性能，因此会使用批量 IO、缓冲、连接复用和合理的线程模型降低开销。

## 4. Redis

### Q18：Redis 常见数据结构和使用场景是什么？

**参考回答：**

String 适合缓存和计数，Hash 适合对象字段，List 可以做简单队列，Set 适合去重和集合运算，Sorted Set 适合排行榜和按分值排序，Stream 可以做更完整的消息流场景。

选择数据结构时要同时考虑命令复杂度、内存占用、过期策略和并发语义。

### Q19：RDB 和 AOF 有什么区别？

**参考回答：**

RDB 是某个时间点的数据快照，文件紧凑、恢复速度快，但可能丢失最近一次快照后的数据。AOF 记录写命令，数据恢复粒度更细，但文件可能更大，需要重写压缩。

生产环境可以根据数据可恢复性和性能要求组合使用，并明确备份、恢复和丢失数据窗口。

### Q20：什么是缓存穿透、击穿和雪崩？

**参考回答：**

缓存穿透是请求查询本来不存在的数据，可以通过参数校验、缓存空值或布隆过滤器缓解；缓存击穿是某个热点 key 过期瞬间大量请求打到数据库，可以使用互斥更新、逻辑过期或预热；缓存雪崩是大量 key 同时失效或缓存服务整体不可用，可以使用随机过期、分批发布、限流和降级。

### Q21：Redis 分布式锁要注意什么？

**参考回答：**

加锁需要唯一 value 和过期时间，释放时必须校验 value 后再删除，避免误删其他持有者的锁。还要考虑业务执行时间超过 TTL、客户端故障、续期、重入和锁服务不可用。

对于强一致的关键业务，不能只凭一个简单 Redis 锁就声称绝对安全，要结合数据库约束、幂等键和事务设计。

### Q22：Redis 为什么快？哪些情况会变慢？

**参考回答：**

Redis 主要在内存中处理数据，数据结构和命令实现高效，网络协议简单。大 key、慢命令、频繁全量扫描、持久化阻塞、内存淘汰和网络带宽不足都可能造成延迟升高。

排查应结合慢日志、命令耗时、内存分析、key 分布、连接数和持久化指标。

### Q23：Redis 过期策略和内存淘汰策略有什么区别？

**参考回答：**

过期策略决定到期 key 何时被实际删除，通常结合惰性删除和定期删除；内存淘汰策略是在达到 `maxmemory` 后决定淘汰哪些 key，例如按最近最少使用或随机淘汰。

过期时间不是数据一定在某个精确时刻消失的承诺，业务不能把 Redis 过期当作精确的定时任务。

## 5. MySQL

### Q24：InnoDB 为什么常用 B+Tree 做索引？

**参考回答：**

B+Tree 的非叶子节点只保存索引信息，叶子节点保存数据或主键引用，树的扇出较大，磁盘 IO 层级较少；叶子节点有序连接，也适合范围查询。

索引不是越多越好，因为会增加写入维护成本、占用空间，并可能让优化器选择不合适的执行计划。

### Q25：MySQL 事务的 ACID 是什么？

**参考回答：**

Atomicity 是原子性，Consistency 是一致性，Isolation 是隔离性，Durability 是持久性。数据库通过日志、锁、MVCC 和约束等机制共同实现这些目标，具体保证依赖存储引擎和配置。

### Q26：MySQL 常见事务隔离级别有什么区别？

**参考回答：**

常见级别包括读未提交、读已提交、可重复读和串行化，隔离性逐步增强，并发性能通常逐步下降。InnoDB 的 MVCC 和锁机制可以减少读写冲突；回答时要说明脏读、不可重复读和幻读分别是什么，以及项目实际使用的隔离级别。

### Q27：什么是 MVCC？

**参考回答：**

MVCC 通过记录版本信息和事务可见性规则，让读操作读取符合当前事务视图的数据版本，减少读写之间的锁冲突。它不是完全不加锁，写写冲突、范围锁和特定查询仍然可能需要锁。

### Q28：如何排查 MySQL 慢查询？

**参考回答：**

先通过慢查询日志定位 SQL，再用 `EXPLAIN` 查看访问类型、候选索引、实际扫描行数、回表和排序情况。之后结合索引设计、SQL 改写、数据分布、分页方式、锁等待和连接池排查。

不能只看到 `EXPLAIN` 中有索引就认为查询一定高效，还要关注实际扫描量和线上数据规模。

### Q29：MySQL 索引失效的常见原因有哪些？

**参考回答：**

常见原因包括对索引列做函数或隐式类型转换、使用前导通配符、联合索引不满足最左匹配、选择性太低、范围条件后无法继续有效使用后续列，以及优化器判断全表扫描成本更低。

最终要结合执行计划和实际数据验证，不能只背规则。

### Q30：MySQL 中有哪些常见锁？

**参考回答：**

可以从表锁、行锁、意向锁、共享锁、排他锁和间隙锁理解。InnoDB 通过行级锁和 MVCC 支持并发，范围查询在特定隔离级别下可能使用间隙锁或临键锁防止幻读。

排查锁问题时查看事务状态、锁等待、长事务和 SQL 执行时间，优先缩短事务范围并保持访问顺序一致。

## 6. Python 基础

### Q31：Python 的 GIL 是什么？

**参考回答：**

GIL 是 CPython 中保护解释器对象状态的互斥机制，同一时刻一个进程内通常只有一个线程执行 Python 字节码。CPU 密集型任务可以考虑多进程、原生扩展或释放 GIL 的库；IO 密集型任务仍适合线程或 asyncio。

GIL 是 CPython 的实现细节，不等于 Python 语言规范。

### Q32：Generator 和 Iterator 有什么区别？

**参考回答：**

Iterator 是实现 `__iter__()` 和 `__next__()` 的协议；Generator 通常通过 `yield` 创建，是一种方便实现 Iterator 的方式。生成器适合流式处理和降低内存占用，但不是所有迭代器都是生成器。

### Q33：装饰器如何工作？

**参考回答：**

装饰器是接收函数并返回新函数的高阶函数，`@decorator` 近似执行 `func = decorator(func)`。使用时要注意 `functools.wraps`、异常处理、类型签名和同步/异步兼容。

### Q34：`*args`、`**kwargs` 和上下文管理器是什么？

**参考回答：**

`*args` 收集位置参数，`**kwargs` 收集关键字参数；上下文管理器通过 `__enter__` 和 `__exit__`，或 `contextlib.contextmanager`，保证资源获取和释放。数据库 session、文件、锁和 tracing scope 都适合使用上下文管理器。

### Q35：Python 的 Lock 和 RLock 有什么区别？

**参考回答：**

`Lock` 是普通互斥锁，同一线程重复获取会阻塞自己；`RLock` 允许同一线程递归获取，但需要对应次数的 release 才能真正释放。只有在确实存在嵌套加锁且锁的所有权清晰时才使用 `RLock`，否则优先通过缩小临界区和统一加锁顺序简化并发关系。

## 7. 并发、消息队列与分布式

### Q36：Kafka 和 RocketMQ 有什么区别？什么时候使用消息队列？

**参考回答：**

消息队列可以用于异步解耦、削峰、广播和可靠重试，但会引入延迟、重复消费、顺序和运维成本。Kafka 更偏高吞吐日志流和分区消费，RocketMQ 常见于业务消息、延迟消息和事务消息场景；具体选择要结合团队生态、消息模型、顺序/事务需求和运维能力。

不要只背产品对比，应该说明消息是否允许重复、是否要求顺序、失败如何重试、积压如何处理。

### Q37：Kafka 到 Flink 如何保证端到端语义？

**参考回答：**

先明确是 at-most-once、at-least-once 还是 exactly-once。Kafka offset 提交、Flink checkpoint、状态恢复和下游 sink 的幂等/事务能力必须一起设计；只开启 Kafka 或 Flink 的某个配置，不能直接宣称端到端 exactly-once。

需要记录 checkpoint、offset、失败重启和下游提交边界，并通过故障注入验证重复、丢失和乱序行为。

### Q38：如何保证消费者不重复处理同一条消息？

**参考回答：**

大多数系统只能做到至少一次投递，因此要在业务层做幂等。可以使用业务唯一键、数据库唯一约束、状态机条件更新、幂等记录表或 outbox/inbox 模式；关键更新和幂等标记要放在同一事务边界内。

“消费成功后再提交 offset”仍可能在进程崩溃时重复消费，所以正确目标通常是重复可安全执行，而不是口头承诺绝对只消费一次。

### Q39：流量变大后，Kafka 会不会变成系统瓶颈？如何处理？

**参考回答：**

会。瓶颈可能来自分区数、单分区吞吐、生产者发送批次、序列化、网络、消费者处理速度、下游数据库或消息积压。可以通过合理分区、批量与压缩、消费者扩容、限流、背压、降级和积压监控处理，但不能只增加线程数。

如果业务会把一个任务拆成大量消息，还要评估消息数量本身、重试风暴和下游频率限制，必要时在业务层合并或采样。

### Q40：动态线程池如何设计？线程池满了怎么办？

**参考回答：**

线程池至少要明确 core size、maximum size、队列容量、keep-alive、线程命名、拒绝策略、任务超时和监控指标。队列不能无界，否则可能用内存换来不可控延迟；线程数也要受 CPU、IO、下游连接数和业务限额约束。

线程池满时可以根据任务重要性选择调用方执行、快速失败、丢弃低优先级任务或进入持久化队列，但必须记录拒绝次数和告警，不能静默丢任务。

### Q41：多机器如何实现限流？令牌桶怎么写？

**参考回答：**

令牌桶按速率补充令牌，请求消耗令牌，允许一定突发但长期速率受限。单机可以用内存和单调时钟，多机需要共享状态，例如 Redis Lua/原子操作，并按用户、接口、租户或全局维度设计 key。

要考虑时钟、网络失败、热点 key、令牌精度和故障时开关策略。限流不能替代幂等、熔断和下游容量评估。

### Q42：主线程如何知道子线程都完成了？

**参考回答：**

可以使用 `join`、`Future`、CountDownLatch、事件或条件变量。选择取决于任务是否需要返回值、是否允许异常传播、是否支持超时和取消；共享状态必须有明确的同步策略。

生产代码还要处理线程异常、超时、取消、优雅关闭和部分任务失败，不能只等待一个“完成计数”。

### Q43：Redis 和 MySQL 数据不一致，如何处理？

**参考回答：**

常见 cache-aside 流程是先更新数据库，再删除缓存；并发和失败窗口下可以结合延迟双删、版本号、消息队列/outbox、订阅 binlog 或重建任务。读路径要考虑缓存击穿，写路径要考虑删除失败和重复消息。

没有一种策略适用于所有业务，要先明确一致性要求、允许的脏数据窗口、读写比例和故障恢复方式。关键数据最终仍以数据库为准，并使用幂等和监控兜底。

### Q44：Redis 热点 key 过期、缓存穿透和缓存雪崩怎么处理？

**参考回答：**

热点 key 可以使用随机 TTL、逻辑过期、互斥重建和预热；不存在的数据可以缓存空值、做参数校验或使用布隆过滤器；大量 key 同时过期或缓存整体不可用时，需要分散过期、限流、降级和分批发布。

处理方案要结合业务可接受的旧数据时间和数据库容量，不能把缓存过期时间当作精确调度器。

### Q45：Redis 的 RDB、AOF、复制和集群分别解决什么问题？

**参考回答：**

RDB 是时间点快照，恢复快但可能丢失最近数据；AOF 记录写命令，恢复粒度更细但文件和重写成本更高；复制用于副本和故障切换；集群主要解决数据分片和容量扩展。

需要分别回答持久化、可用性和扩展性，不能把“有副本”直接等同于“数据不会丢”。

### Q46：一次 MySQL 修改会涉及哪些日志？

**参考回答：**

InnoDB 通常涉及 redo log、undo log 和 binlog：redo 用于崩溃恢复，undo 用于回滚和 MVCC，binlog 主要用于复制和增量恢复。事务提交时需要协调存储引擎日志与 binlog 的持久化边界，具体顺序和刷盘行为还受配置影响。

回答时要区分日志用途、内存缓冲和持久化，不要把所有日志都笼统说成“用来恢复”。

## 8. LeetCode、算法与手撕题

### Q47：如何判断括号是否有效？

**参考回答：**

使用栈保存左括号，遇到右括号时检查栈顶是否匹配，最后要求栈为空。时间复杂度是 `O(n)`，空间复杂度最坏是 `O(n)`。需要覆盖空串、前缀右括号、嵌套和混合括号。

### Q48：如何找到未出现的第一个正整数？

**参考回答：**

数组长度为 `n` 时，可以把值 `x` 放到下标 `x - 1` 的位置，只处理 `1 <= x <= n`，再扫描第一个位置不匹配的下标。通过交换或循环归位实现 `O(n)` 时间和 `O(1)` 额外空间，必须注意重复值、负数和越界值导致的死循环。

### Q49：三数之和怎么做？

**参考回答：**

先排序，固定第一个数，再用左右指针寻找另外两个数，并跳过重复值。时间复杂度为 `O(n^2)`，除排序外额外空间通常为 `O(1)`。要说明是否要求去重、是否允许整数溢出以及结果规模。

### Q50：所有子数组中位数之和怎么优化？

**参考回答：**

先确认偶数长度的中位数定义、数据范围和是否要求精确结果。朴素做法枚举子数组并排序，复杂度很高；固定左端点向右扩展时，可以用平衡树、双堆或有序结构维护中位数，通常能降到 `O(n^2 log n)`。

如果 `n` 很大，需要进一步利用值域、二分和计数等方法，但不存在脱离约束的一句通用最优解。面试时应先澄清规模，再给出可验证的复杂度。

### Q51：如何实现 LRU？

**参考回答：**

使用 HashMap 保存 key 到链表节点的映射，双向链表维护最近使用顺序。访问或更新节点时移动到头部，容量满时删除尾部节点，`get` 和 `put` 平均为 `O(1)`。

需要处理更新已有 key、容量为零、重复删除和并发访问；并发版本还要明确锁粒度和淘汰的一致性。

### Q52：如何按规则压缩字符串？

**参考回答：**

使用双指针或一次扫描统计连续相同字符，输出字符和计数，例如把连续段编码为 `a3`。要先确认单字符是否输出计数、数字字符如何转义、是否要求原地修改和输出长度是否可能增长。

### Q53：如何查询至少连续出现三次的记录？

**参考回答：**

先定义“连续”是按自增 id、时间还是业务序列。SQL 可以用 `LAG`/`LEAD` 窗口函数比较前后记录，也可以用行号分组或自连接；如果要求连续 id，必须同时检查 id 是否真的相邻，不能只按排序后的行位置判断。

### Q54：手撕题如何回答时间复杂度和优化？

**参考回答：**

先说明输入规模、时间限制、是否允许额外空间和结果是否需要排序/去重，再给出基线解法和瓶颈。优化时从重复计算、排序、哈希、双指针、滑动窗口、堆、二分和空间换时间等方向选择，并用边界用例验证。

## 9. Vibe Coding 与 AI 辅助开发

### Q55：什么是 Vibe Coding？它和正常软件工程有什么区别？

**参考回答：**

Vibe Coding 可以理解为用自然语言和 AI 协作快速生成代码，但工程师仍然要负责需求澄清、架构边界、接口契约、测试、部署和维护。它适合原型和重复代码，不意味着可以跳过设计、review 和质量验收。

好的回答要讲清 AI 生成、人工约束、自动验证和失败回滚的闭环，而不是说“以后不需要写代码”。

### Q56：用 AI 生成二叉搜索树的构建、遍历和格式化打印，如何验收？

**参考回答：**

先明确节点结构、重复值策略、空树输出、遍历顺序和打印格式，再让 AI 分步生成。验收至少覆盖空树、单节点、平衡树、退化树、重复值和负数；检查中序遍历有序性、插入结果、删除后结构和复杂度。

如果需要手写删除节点，要覆盖叶子、单子树和双子树三种情况，并用回归测试证明删除前后的 BST 性质仍成立。

### Q57：如何保证 AI 生成代码不是“看起来能跑”？

**参考回答：**

先让模型说明假设和接口，再查看 diff、类型、异常、资源释放和复杂度；随后运行 formatter、lint、单测、属性测试和集成测试，必要时做基准和人工 review。生成代码必须进入版本控制和可回滚流程，不能直接覆盖生产文件。

### Q58：如果让你做一个带 TUI 的交互式视频剪辑 MVP，如何用 AI 辅助？

**参考回答：**

先由人确定 MVP、领域状态、媒体处理边界和验收用例，再让 AI 分模块生成 TUI、任务调度、预览和导出代码。长任务要有进度、取消和失败恢复，AI 生成的模块必须分别测试，不能把一次大 prompt 的输出直接当作完整系统。

## 10. 大模型与 Transformer 基础

### Q59：Self-Attention 为什么拆成 Q、K、V？

**参考回答：**

Q 表示当前位置想查询什么，K 表示各位置可匹配的特征，V 表示被聚合的内容。典型计算是 `softmax(QK^T / sqrt(d_k))V`，先用 Q/K 得到相关性，再对 V 加权求和。

### Q60：同一个 token 在不同位置的向量一样吗？为什么需要位置编码？

**参考回答：**

词表 embedding 对同一个 token 可以相同，但加入绝对位置编码或旋转位置编码后，模型表示会包含位置信息。没有位置表示，纯 self-attention 很难区分词序，无法充分理解“谁修饰谁”和前后关系。

### Q61：为什么需要 Multi-Head Attention？Q、K、V 为什么不直接相同？

**参考回答：**

不同 head 可以在不同投影空间学习语法、指代和长距离关系。Q、K、V 通过不同的可学习矩阵投影，即使来自同一个 token 也承担查询、匹配和内容表示的不同职责；注意力输出本质上是依赖输入的动态加权。

### Q62：temperature 和 top_p 分别有什么作用？

**参考回答：**

temperature 调整 logits 分布的尖锐程度，较低通常更确定；top_p 从累计概率最高的一组候选中采样。它们都影响随机性，但具体效果取决于 provider、采样实现和其他参数，不能把 temperature 设为 0 说成绝对确定。

### Q63：KV Cache、Continuous Batching 和 vLLM 解决什么问题？

**参考回答：**

KV Cache 在自回归生成时复用已经计算过的 key/value，减少重复计算，但会消耗显存并受上下文长度影响。Continuous Batching 动态合并不同请求，提升 GPU 利用率；vLLM 等推理框架会围绕 KV 管理和批处理做优化。

回答时要同时说明吞吐、首 token 延迟、显存、并发和请求长度之间的取舍，不能只说“用了就更快”。

### Q64：Transformer 的基本组成是什么？

**参考回答：**

通常包括 token embedding、位置表示、self-attention、前馈网络、残差连接和归一化；语言模型还会使用 causal mask 防止看到未来 token。编码器、解码器或 decoder-only 结构的差异要结合任务说明。

## 11. Java 与 C++ 补充

### Q65：Java 17 相比旧版本有哪些值得关注的变化？

**参考回答：**

回答应围绕实际使用的特性，例如 record、sealed class、文本块、模式匹配的演进，以及长期支持版本带来的维护价值。不要把预览特性当成所有 Java 17 环境默认可用，最好说明编译版本和项目是否真正使用。

### Q66：C++ 多态是如何实现的？

**参考回答：**

运行时多态通常依赖虚函数和虚函数表：基类通过 `virtual` 声明接口，子类重写后经由基类指针或引用调用实际实现。使用基类指针删除子类对象时要考虑虚析构函数，避免资源释放不完整。

### Q67：向量数据库和 MySQL 的职责有什么区别？

**参考回答：**

MySQL 更适合事务、结构化字段、权限和权威事实；向量数据库更适合根据 Embedding 做语义近邻召回。RAG 通常先用关键词或结构化过滤缩小范围，再使用向量召回和 rerank，最终仍要回到权威数据和来源引用。

向量库不是 MySQL 的替代品，也不能因为相似度高就绕过成员隔离、权限校验和事实来源。具体项目要说明真实使用的数据库、Embedding、索引和降级方案；没有实际接入时不能虚构线上效果。

### Q68：不用加减乘除实现两数之和，怎么做？

**参考回答：**

异或可以得到不进位的和，按位与再左移一位可以得到进位。循环执行 `sum = a ^ b`、`carry = (a & b) << 1`，直到进位为零。

在 Python 中负数按无限位补码处理，如果题目要求 32 位整数，需要加掩码限制位数，并在最后把结果还原成有符号整数。面试时要先问清整数位数和溢出规则。

### Q69：最长递增子序列怎么做？动态规划方程是什么？

**参考回答：**

基础动态规划定义 `dp[i]` 为以第 `i` 个数结尾的最长递增子序列长度。如果 `nums[j] < nums[i]`，就用 `dp[j] + 1` 更新 `dp[i]`，时间复杂度是 `O(n^2)`。

进一步可以维护一个数组，记录不同长度递增子序列的最小结尾值，再用二分查找更新，时间复杂度降为 `O(n log n)`。这个数组不一定就是最终的递增子序列；如果题目要求还原序列，需要额外保存前驱关系。

### Q70：合并 K 个升序链表怎么做？

**参考回答：**

常见做法是把每条链表的头节点放入最小堆，每次取出最小节点并把它的下一个节点加入堆。总节点数为 `N`、链表数为 `k` 时，时间复杂度是 `O(N log k)`，堆空间是 `O(k)`。

另一种做法是两两分治合并，复杂度同样是 `O(N log k)`。回答时要注意空链表、相同节点值，以及不同语言中堆比较节点对象的方式。

### Q71：日志文件很大，内存放不下，怎么找出 ERROR 数最多的前五个文件？

**参考回答：**

按文件流式读取，一次只保留当前行和当前文件的计数，不能把日志整体读入内存。每个文件统计完成后，把“文件名和 ERROR 数量”放进容量为五的最小堆，最后得到前五名。

文件很多时可以按文件并行，但要限制并发数，避免磁盘随机读取和文件句柄成为瓶颈。还要处理编码错误、超大单行、文件读取失败和统计期间文件继续写入的问题，并明确统计的是快照还是实时结果。

### Q72：后台有大量定时任务，怎么设计高性能定时器？

**参考回答：**

精度要求不高、任务量很大时可以用时间轮，把任务按到期时间放入不同槽位；需要更精确地找到最近任务时，可以配合最小堆。任务索引用 HashMap 保存，便于取消和更新。

工程上还要考虑时钟回拨、任务重复执行、长任务阻塞调度线程、失败重试和持久化恢复。调度线程只负责发现到期任务，实际执行交给有界线程池，不能在时间轮里直接跑耗时业务。

### Q73：动态有向无环图的最大路径值怎么求？

**参考回答：**

静态有向无环图可以先拓扑排序，再按拓扑顺序做动态规划：每个节点的最大值由所有前驱节点的结果转移而来。如果拓扑排序无法处理完所有节点，说明图中存在环。

动态图新增边或修改权重后，简单方案是重新拓扑排序和计算；需要增量优化时，只更新受影响的后继区域，但实现和正确性证明更复杂。面试时要先问“动态”是改权重、加边还是删边，以及是否始终保证无环。

### Q74：AI Coding 限时做一个前后端聊天应用，你会怎么推进？

**参考回答：**

先收敛最小功能：创建会话、发送消息、流式显示、保存历史和错误重试。然后确定接口和数据结构，再分别完成后端会话接口、模型调用、前端消息列表和流式连接，最后补基本测试和异常处理。

限时场景下可以用 AI 生成脚手架和重复代码，但我会先检查依赖、接口、权限和数据流，再运行代码逐步验收。流式输出可以根据场景选择 SSE 或 WebSocket；还要限制并发、请求大小和历史长度，不能只做一个能展示的页面。

### Q75：设计聊天系统时，怎么保证消息顺序和不重复？

**参考回答：**

客户端为每条消息生成唯一消息编号，服务端按会话维护递增序号，并以消息编号做幂等。发送成功前先持久化，再投递后续处理；重复请求返回原结果，而不是再次生成或写入。

多服务器环境下可以按会话分片，让同一会话尽量进入同一处理分区；跨服务通过消息队列解耦时，要接受至少一次投递，并在消费端去重。全局绝对顺序成本很高，通常只保证单个会话内有序。

### Q76：怎么实现第 K 个最大元素？什么时候用堆，什么时候用快速选择？

**参考回答：**

容量为 `k` 的最小堆适合流式数据或需要持续维护前 `k` 大元素，时间复杂度是 `O(n log k)`。快速选择通过分区把目标位置放对，平均时间复杂度是 `O(n)`，更适合一次性处理数组，但最坏情况可能退化。

面试时要说明是否允许修改原数组、数据是否持续到来、是否要求稳定顺序和最坏复杂度保证。

### Q77：Vibe Coding 时怎么审核 AI 生成的整体架构？

**参考回答：**

先从入口请求走一遍完整链路，看模块职责、数据所有权、外部依赖和失败路径是否清楚；再检查接口是否稳定、有没有循环依赖、状态是否被多个模块同时修改，以及安全和权限是否放在正确边界。

随后用小步提交、代码 review、静态检查、单元测试和端到端用例验证。AI 可以加快实现，但架构判断、风险取舍和最终验收仍由工程师负责。

### Q78：动态规划的核心思路是什么？怎么写状态转移方程？

**参考回答：**

先定义状态表示什么，再找当前状态和更小子问题之间的关系，然后确定初始值和计算顺序。状态转移方程不是背出来的，而是把“最后一步怎么选”写成数学关系。

例如最长递增子序列中，`dp[i]` 表示以第 `i` 个数结尾的最长长度，只能从值更小且位置更靠前的状态转移。还要说明是否存在重复子问题、能否压缩空间，以及记忆化搜索和自底向上动态规划的区别。

### Q79：单服务器和多服务器分别怎么提高性能？

**参考回答：**

先通过监控和压测定位瓶颈。单服务器可以优化数据库索引、缓存、连接池、批处理、异步 IO 和热点代码；多服务器则需要服务尽量无状态，通过负载均衡水平扩容，并把会话、任务和文件放到共享存储或按规则分片。

扩容后还要处理幂等、限流、数据一致性和故障转移。不能只说“加机器”，因为瓶颈可能转移到数据库、日志、消息队列或外部模型服务。

### Q80：高并发下日志怎么设计，避免日志本身成为瓶颈？

**参考回答：**

业务线程只写入有界缓冲区，由独立线程批量落盘，并按大小或时间滚动文件。日志使用结构化字段和请求编号，方便检索和串联链路；高峰期还要定义背压、采样和丢弃低等级日志的策略。

多线程不能直接无序写同一个文件。可以使用线程安全队列加单写线程，或者每个线程先写局部缓冲再合并。错误日志和审计日志不能随意丢弃，普通调试日志则可以降采样。

### Q81：高并发下给所有用户的问题消息做统一计数，怎么实现？

**参考回答：**

先确认要求精确计数还是近似统计。单机精确计数可以用原子变量、`LongAdder`，或者让每个线程维护局部计数后定期汇总，减少同一个共享变量上的竞争。

多机环境通常按用户或时间分片，再通过消息队列或存储系统聚合。还要明确重复消息怎么去重、统计窗口多大、服务重启后是否需要恢复，不能只讨论一个内存变量。
