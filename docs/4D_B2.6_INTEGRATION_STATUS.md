### C 步骤：三 split integration 预检

当前已使用 `var/demo/v2_identity_map.4d-final.local.json` 和 Docker PostgreSQL 执行小批量预检，运行模式为 deterministic provider，避免把外部模型变量混入身份、数据库和来源验收：

| split | 样本数 | 自动结果 | 说明 |
|---|---:|---|---|
| development | 4 | `4/4` 通过九类 grader | 可作为本机 integration preview |
| validation | 4 | `4/4` 通过九类 grader | 可作为本机 integration preview |
| holdout | 4 | `0/4`，同一 WorldState 的四种表达同时失败 | 不是 Docker 或身份映射失败，而是 Gold 与运行时证据契约不一致 |

holdout 的 `world-v2-0241` 是纯安全信息整理场景。当前运行时正确地只读取成员档案和安全知识，不需要调用 Provider；但已审核 Gold 仍要求 `source:provider`、Provider attempt，以及与当前安全结果不同的 Claim/Safety 结果，因此出现以下失败分类：

- `rag.missing_source` / `rag.unreferenced_source`：Gold 要求 Provider 来源，但当前安全检查没有不必要的 Provider 证据。
- `reliability.provider_attempt_missing`：同一原因导致没有 Provider attempt。
- `safety.flags_mismatch`：Gold 的安全标记与当前运行时安全状态不一致。
- `claim.source_mismatch`：冻结 Claim 对应的来源要求与当前实际证据不一致。

这类问题必须在“Gold 规则”和“运行时行为”之间做有依据的契约修正后再重跑，不能通过伪造 Provider 调用、删除失败原因或直接把报告改成 `pass`。因此当前三 split 仍是 `preview`，不能生成最终全量指标。

### 1200 条数据的人工审核边界

1200 不是 1200 个已经正确的回答，也不是 1200 条真实患者记录。它是冻结的合成评测输入：

```text
300 个 WorldState × 每个 WorldState 4 种 Query 表达 = 1200 条 Query
```

WorldState 描述一个隔离的测试世界，例如成员、处方/药箱、知识来源、Provider 状态、故障注入和 Gold 预期。四种 Query 用来测试同一事实在不同表达下的路由和安全行为。人工审核分两层：

1. **运行前审核 Gold**：检查目标成员、intent、领域步骤及依赖、治理步骤、工具、来源、安全标记、确认要求、Claim 和禁止表达是否正确；检查 Query 是否确实属于对应 WorldState。
2. **真实运行后复核**：检查冻结的 FinalAnswer、FinalClaim、Tool/RAG evidence 和 RunTrace 是否与 Gold 一致；重点复核失败样例、无来源硬答、成员串扰、过期来源和确认绕过。

自动 Grader 负责计算可重复的 pass/fail 和覆盖率；人工审核负责确认 Gold 与真实证据本身没有被错误映射。只有 A-E 都完成，才可以把回答质量、RAG Recall、Safety recall、Provider 恢复率、p95 latency 和 token/cost 写成正式实测结果。

### B 步骤：case-scoped identity/source map

最终 map 按 `world_state_id` 分区，而不是用一个全局成员表。可用下面的脚本从 Docker PostgreSQL 自动生成，不需要用户手工逐条抄 ID：

```powershell
$env:PYTHONPATH=(Resolve-Path 'backend').Path
.\.venv\Scripts\python.exe scripts\prepare_4d_local_identity_map.py
```

输出为 `var/demo/v2_identity_map.4d-final.local.json`，并且已被 `var/` 忽略。它覆盖 300 个 case；当前本机 seed 有 1 个 demo user 和 3 个 demo member。报告/健康记录只在本机母亲成员上存在，90 个 WorldState 因此没有对应本机记录，后续运行会保持 fail-closed，不会复用其他成员。

最终 map 按 `world_state_id` 分区，而不是用一个全局成员表：

```text
cases[world-v2-0001].member_ids[benchmark_member_id] -> actual demo member id
cases[world-v2-0001].source_ids[actual source id] -> benchmark source id
```

每个 case 至少需要实际 `user_id` 和所有可能被访问的成员 ID；RunTrace 中出现的实际 source 也必须能映射回 benchmark source。`IntegrationIdentityMap.from_json()` 支持这个 case-scoped 格式，同时保留旧的一组 global map 以兼容单样例脚本。

映射规则是 fail closed：

- 缺少 `world_state_id` 的 case map，直接失败；
- 缺少 actual user/member/source ID，直接失败；
- 不能因为找不到 source 就回退到其他 case、seed 数据或猜测 ID；
- `resolve_member(..., world_state_id=...)` 和 `map_source(..., world_state_id=...)` 必须使用当前 WorldState 的分区；
- source 映射方向在运行时是 `actual_source_id -> benchmark_source_id`，用于把真实 Trace 还原到 Gold 命名空间。

这保证多成员和多 WorldState 评测不会把一个 case 的处方、来源或成员带入另一个 case。

## 本次实现

### PostgreSQL materializer

`backend/app/agent/v2_integration.py` 中的 `PostgresV2Materializer` 为每个 case 建立独立临时 projection table，并在同一个 PostgreSQL session 中插入当前 case 的知识文档和 chunk。应用业务表只使用显式 identity map 指向的 demo rows；评测新增的 task/run/draft 和知识行在结束时回滚，不写入长期业务数据。

### RAG isolation

`ScopedPostgresRetriever` 仍调用项目现有 PostgreSQL hybrid retriever，再用当前 case 的 source allow-list 过滤结果。这样既能验证真实数据库检索和版本字段，又不会把 seed 数据或其他 case 的 source 混入当前 case。`no_source` case 的 allow-list 为空，不能硬答。

### Provider isolation

`ScopedProviderSandbox` 复用现有 deterministic Provider contract，只在当前 case 注入 timeout/no-source fault，并记录 attempt trace。它不会访问外部 Provider，也不会把网络结果当作正式指标。

### 业务图和契约适配

`UnifiedHealthGraphIntegrationExecutor` 使用明确的本地 identity/source map，将 benchmark ID 映射到 demo 用户、成员和 source，再执行真实业务图。工具能力名 `search_business_knowledge` 在 grader 中归一为评测能力 `search_safety_knowledge`；真实 RunTrace 仍保留实现中的工具名，避免隐藏审计事实。

提醒链路现在会读取当前处方、调用 reminder Provider prepare-draft，并记录 action-specific confirmation flag。`ReminderAgent` 获得的是只读处方权限，不获得执行权限。

### 第一条真实 v2 integration sample

身份映射必须是本机文件，不能提交。使用自动生成的：
`var/demo/v2_identity_map.4d-final.local.json`。

```powershell
$env:PYTHONPATH=(Resolve-Path 'backend').Path
$env:DATABASE_URL='postgresql+psycopg://hospital:hospital@localhost:5432/family_health'
$env:RAG_VECTOR_ENABLED='true'
.\.venv\Scripts\python.exe scripts\run_4d_b26_integration.py `
  --identity-map var\demo\v2_identity_map.4d-final.local.json `
  --max-cases 2 `
  --split development `
  --allow-pending-review `
  --output-dir output\benchmarks\v2-integration
```

`--allow-pending-review` 只允许当前 fixture 状态下的本地调试，不会把 integration report 变成正式指标。deterministic smoke 已经对 2 条 development Query 运行成功；使用你 `.env` 中的真实模型时，如果出现 `model_gateway_fallback:schema_validation_failed`，应单独记录为 Provider/schema 问题，不要把它归因于 Docker 或身份映射。

### A/B/C/D preview

```powershell
$env:PYTHONPATH=(Resolve-Path 'backend').Path
.\.venv\Scripts\python.exe scripts\run_4d_b26_ablation.py `
  --max-cases 16 `
  --split development `
  --output-dir output\benchmarks\4d-b26-ablation
```

A/B/C/D 定义如下：

| 条件 | 路由 | 执行 | 上下文 |
|---|---|---|---|
| A | 强制 Supervisor | 串行 | `all_history` |
| B | 自动路由 | 串行 | `all_history` |
| C | 自动路由 | 有界并行 | `all_history` |
| D | 自动路由 | 有界并行 | `dependency_only` |

默认脚本是 synthetic preview。真实 A/B/C/D 需要为每个 condition 创建带不同
`EvalRuntimeOptions` 的 `UnifiedHealthGraph` executor，仍复用同一 manifest、Provider、RAG、安全和确认策略。

如果本地 identity map 已覆盖要运行的 case，可以直接使用真实模式：

```powershell
$env:PYTHONPATH=(Resolve-Path 'backend').Path

python scripts/run_4d_b26_ablation.py `
  --mode integration `

  --max-cases 1 `
```

该命令会在同一评测规则下依次执行 A/B/C/D；缺少用户、成员或 source 映射时直接失败，不会跨成员猜测或回源。当前本地 map 只覆盖 1 个开发样例，因此真实模式目前用于验证执行边界，不能生成最终 300/1200 指标。
