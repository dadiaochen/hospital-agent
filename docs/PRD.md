# 家庭健康服务 Multi-Agent 产品需求文档

## 1. 产品定位

本项目来源于互联网医院业务场景，面向患者及其家庭成员提供就医前信息整理、慢病与用药履约辅助、报告解读和长期健康档案服务。

系统不是 AI 医生，不做疾病诊断，不自动开方，不修改医生处方，也不建议用户自行加量、减量、停药或换药。涉及复诊申请、购药、提醒创建等关键动作时，系统可以自动生成没有外部副作用的本地待确认草稿，用户只确认真正的执行动作；涉及诊断、严重症状和用药调整时，必须经过三层安全治理并引导医生或人工处理。

## 2. 用户与核心价值

主要用户是患者本人和代管父母健康事务的家庭成员。系统解决三类问题：

1. 就医前信息分散，患者难以完整描述症状、既往史和就医诉求。
2. 慢病续方、药箱盘点、购药和提醒需要在多个入口之间反复核对。
3. 检查、体检和中医舌诊等报告难以理解，也缺少连续、按成员隔离的健康记录。

核心价值不是替用户做医疗决定，而是把信息、证据、待确认事项和下一步操作整理成可追踪的任务。

## 3. 三条业务主线

### 3.1 智能预问诊与分级导诊

- 根据患者主动输入整理主诉、持续时间、伴随症状、既往史和就医诉求。
- 识别缺失信息并进行有限轮次追问。
- 根据医院科室、线上问诊能力和权威导诊规则生成候选就医路径。
- 命中严重症状或高风险规则时停止普通导诊，提示及时线下就医或急诊。
- 输出预问诊摘要、缺失项、风险提示、候选科室和来源引用，不输出诊断结论。

### 3.2 家庭医生、慢病与用药履约

- 按家庭成员查询健康档案、历史处方、药箱余量和购药记录。
- 整理续方、复诊、购药、库存查询和用药提醒的待确认草稿。
- 支持用药咨询中的相互作用与禁忌规则检索；信息不足或风险较高时转医生或药师确认。
- 任何购药、复诊和提醒动作都必须经过用户确认，系统不自动提交外部业务。
- 输出事实、规则说明、待确认方案、安全提示和来源引用。

### 3.3 报告解读与长期健康档案

- 接收检查报告、体检报告、中医诊断材料和舌诊结果等医疗文档。
- 通过文档解析服务提取结构化指标，并结合权威知识解释指标含义和复查提示。
- 报告结论与医生原文保持可追溯，不把模型解释写成诊断事实。
- 经用户确认后，把结构化指标、报告版本和来源引用写入对应家庭成员的长期档案。
- 输出报告摘要、异常指标解释、需医生确认项、纵向变化提示和来源引用。

详细流程见 [BUSINESS_WORKFLOWS.md](BUSINESS_WORKFLOWS.md)。

## 4. RAG 与证据要求

RAG 是三条业务线共用的知识与证据能力，解决四个核心问题：

1. 降低幻觉：医疗流程、安全规则和指标解释不能只依赖模型记忆。
2. 知识可更新：通过更新知识文档和版本调整规则，无需重新训练模型。
3. 答案可追溯：关键解释必须保留 `SourceRef`、文档版本和检索方式。
4. 方便评测：Agent 评测可以检查应引用的知识是否命中、答案是否有证据支持。

处方、库存、病史和报告原文等患者事实必须来自数据库或业务接口；RAG 主要提供医疗流程、安全规则、药品规则和指标解释。模型推断不能替代事实来源。

最终版本以 Embedding 模型驱动的语义向量检索作为主要召回能力。关键词检索用于药品名、检查指标、标准编号、安全词等精确匹配场景，并在向量链路不可用时承担降级兜底。普通自然语言问题默认采用混合检索，对向量与关键词结果去重、重排并校验文档版本和来源。

## 5. 共享业务约束

- 所有请求必须携带当前用户和家庭成员上下文。
- 切换成员时创建新的隔离上下文，不复用上一成员的处方、病史、药箱或报告。
- 所有工具通过 Tool Registry 调用并记录版本、运行模式、输入、输出、耗时、错误和证据引用。
- 外部能力通过 Provider Adapter 接入，按 `mock`、`sandbox`、`real` 区分运行模式。
- 所有用户可见答案必须通过结构化输出校验和 Agent 安全检查。
- 每次运行冻结最终答案、工具证据、RAG 来源、运行轨迹和单次 Agent 评测结果。

## 6. 最终交互与 Agent 范围

- 简单单领域请求直接进入 Triage、Medication 或 Report 领域 Agent。
- 只有复杂跨领域请求才调用一次性 TaskPlanner 和 bounded Supervisor；编排内核已对依赖就绪、只读且无副作用的步骤执行有界 DAG，业务写操作和确认仍串行。
- 依赖已满足、只读且无副作用的领域步骤可以受控并行；确认、写操作、Checkpoint、Agent 安全和 Agent 评测必须串行。
- 三个领域 Agent 各自具有受枚举和工具权限限制的决策点；旧 Profile/Refill/Pharmacy/Reminder 角色收敛为 Medication 领域步骤或 Tool。
- 无 Key 使用 deterministic policy；真实模型只能从固定候选项中输出结构化决策。
- 请求前 Safety Guard、动作前 Policy Guard、最终输出 SafetyAgent 由状态图强制执行。
- 待确认任务使用同一 task 下两次独立 run，PostgreSQL 保存权威 checkpoint，Redis 只做 TTL 缓存和多实例协调。

## 7. 当前完成度

当前仓库已经实现旧版四场景基线：父亲降压药续方、母亲中医复诊材料整理、母亲用药提醒和高风险用药调整拦截。已完成数据库、API、Tool Registry、关键词 RAG 基线、Model Gateway、有界 LangGraph 工作流、运行轨迹、Agent 评测和前端演示页面。

新三条业务主线仍处于本地 MVP 阶段，尚未接入真实医院、药店或生产用户。当前已经完成产品重基线、业务域、Provider 模式、SourceRef、向量 RAG 路径、旧版有界工作流、Model Gateway、任务五的最终路由契约、任务六的 deterministic 三领域编排内核、任务七的新业务三层安全和确认状态机、任务八的 PostgreSQL 权威 checkpoint/Redis 回源/两次 run 续跑、任务九 Tool/Provider 可靠性、任务十 RRF/版本拒绝/成员隔离/脱敏 Observation、任务十一 32 条 deterministic Harness/A/B/C 消融、任务十二真实 Docker 后端验收、任务十三 4B Git/文档收口和 4C 患者端交付，以及 4D-B2.1 的 UnifiedHealthGraph 统一入口、4D-B2.2 的有界只读 DAG 与评测 `all_history` 基线、4D-B2.3 的 FinalClaim/AnswerEnvelope/Trace v2 和 4D-B2.4 的 300/1200 v2 数据生成。v2 数据仍待人工审核、物化和 grader；真实 Provider/LLM、生产认证和部署准备仍是后续可选或生产化工作。

## 8. 验收原则

- 功能验收：三条主线均能形成结构化、可追踪、可确认的业务结果。
- 安全验收：高风险医疗请求被拦截，关键动作无确认不得执行。
- 来源验收：关键医疗解释具备有效来源，患者事实来自数据库或业务接口。
- 隔离验收：跨成员数据不串扰，来源和工具证据均绑定对应成员。
- 评测验收：同时覆盖任务完成、工具调用、RAG 证据、安全、确认、隔离和延迟。
- 真实性验收：未接入的医院、药店、医生、通知和文档解析能力必须明确标记为模拟，不得伪装成实时生产数据。
- 多 Agent 验收：32 条固定用例公平比较 Single Agent、固定领域子图和按需 Planner + bounded Supervisor；简单和复杂任务分开统计。
- 最终架构验收：在同一 300 个 WorldState、1200 条表达上比较自动路由、串行/并行和全历史/最小上下文模式；按 base world 拆分数据，禁止同一事实的表达变体跨集合泄漏。
