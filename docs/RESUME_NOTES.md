# 互联网医院多 Agent 项目：简历与面试口径

本文只保留当前可直接使用的项目表达。阶段过程和旧指标见 [项目执行历史](EXECUTION_HISTORY.md)。

## 1. 业务背景与问题

慢病续方、家庭药箱、用药提醒和报告解读会同时涉及成员身份、历史处方、药品库存、医疗规则和人工确认。单个通用 Agent 容易混合不同来源，在复杂任务中漏步骤、越权调用工具或跳过确认。

本项目把这些请求实现为可追踪、可恢复、可评测的健康事务流程。系统只整理信息、检索依据、生成方案草稿并等待确认，不替代医生诊断、开方或调整用药。

## 2. 为什么使用多 Agent

- 分诊、用药和报告解读需要不同数据、工具和安全边界，按领域拆分后可以最小授权。
- 简单请求直接进入一个领域 Agent，避免无意义的规划成本。
- 复杂任务只规划一次，再由 Supervisor 按冻结依赖调度，避免模型循环改写目标。
- Agent 安全与 Agent 评测是固定治理节点，Supervisor 不能选择或跳过。

## 3. 实现 Pipeline

用户与成员校验 → 请求安全检查 → Router → 简单任务直达 / 复杂任务进入一次性 Planner → Supervisor 有界调度分诊、用药、报告 Agent → 统一工具调用层读取数据库、Provider 和 RAG → 动作安全检查 → 本地草稿与人工确认 → Model Gateway 生成结构化回答 → 最终安全检查 → 冻结回答与运行轨迹 → 上下文重置 → 只读 Agent 评测。

关键技术：

- PostgreSQL 保存权威 Task Checkpoint 和确认版本；Redis 只做 TTL 缓存，失效或故障时回源 PostgreSQL，确认通过新的 run 续跑。
- 每个 Agent 只接收当前成员和任务需要的最小上下文，通过统一工具调用层访问事实，并执行权限、schema、超时、重试和审计。
- RAG 使用 FastEmbed、pgvector HNSW 与 BM25 双路召回，RRF 融合后执行版本过滤、实体筛选、轻量 rerank 和来源校验。
- 入口、动作前和最终回答前三层 Agent 安全固定在图中；购药、续方和提醒只能生成待确认草稿。

## 4. 简历一句话

设计并实现面向互联网医院慢病续方与家庭用药场景的有界多 Agent 系统，以 Router、一次性 Planner 和 Supervisor 编排三个领域 Agent，通过统一工具调用层、PostgreSQL 权威 Checkpoint、Redis 故障回源、三层 Agent 安全和可追溯 RAG，完成任务恢复、人工确认与自动化评测闭环。

## 5. 指标优化写法

**RAG 检索与回答质量（可写简历）：** 针对互联网医院规则检索中精确实体被语义相似片段挤出前排，以及多片段问题中步骤、例外证据错配导致模型拒答的问题，在 125 个基础 Case、500 条冻结合成 Query 上实现 BM25 + pgvector HNSW 双路召回、RRF、活动版本/实体过滤、候选 20 条轻量重排和步骤/例外证据角色选择；Recall@3/@5 从 67.50%/85.19% 提升至 100%/100%，来源绑定回答正确率从 74.69% 提升至 99.69%，260 条可回答题的 RAGAS Faithfulness/Response Relevancy 达到 0.9837/0.6818。以上是无人工审核的合成工程指标，不代表临床效果。

**Agent 闭环稳定性（可写简历）：** 针对阻断/确认状态混用、空知识被误判成功、知识工具未按 Case 隔离和失败后提前中止独立步骤的问题，增加空来源 fail-closed、case-scoped RAG 与冻结 DAG 调度；在 400 条冻结 WorldState Gold 的真实 LLM 全链路评测中，最终回答合同正确率达到 100.00%，端到端任务成功率达到 99.25%，P95 延迟为 6.65 秒。最终回答正确率是业务合同工程指标，不是临床准确率。

**不包装为优化：** 固定 Precision@3/@5 为 43.59%/26.15%，已达到每题必需 Gold 数量决定的理论上限；AI 自动扩展标签的 60.51%/50.15% 是标签覆盖诊断，不是算法收益。Cross-Encoder、真实 LLM 重排和查询扩展均未提高冻结 Gold，继续作为否定实验留档。平均 token 与成本分别上升 15.88%/14.99%，不能写成本下降；Response Relevancy 0.6818 仍低于项目目标 0.70，不能写成达标。

5A-9 的历史 Agent 确定性集成复测使用统一数据集的 300 个 WorldState、1,200 条 Query，经过 PostgreSQL 隔离事务和实际 `UnifiedHealthGraph`，不调用真实 LLM。当前活动评测已缩减为 fast-400（100 个 WorldState、400 条 Query，240/80/80），后续只使用该视图。历史校准结果用于证明工程链路契约，不作为真实模型回答质量或临床准确率。

真实 LLM fast-400 复测已完成：3 条冒烟稳定通过后，按 40 条可恢复批次完成 400 条 Query。冻结业务状态 Gold 自动评分显示：最终回答正确率为 100.00%，端到端任务成功率为 99.25%（397/400），端到端 P50/P95/P99 为 4,294/6,645/7,850 ms。3 条失败均为远程 Provider timeout/HTTP error 触发 fallback；最终回答正确率是合成业务 Gold 的工程正确率，不是临床准确率。

**简历写法：** 构建统一 Agent 评测 Harness，接入 PostgreSQL 隔离事务、case-scoped RAG、真实 OpenAI-compatible LLM 和 Provider 故障记录；通过空来源 fail-closed、确认状态收口与冻结 DAG 调度，在 400 条合成业务 Gold 上实现最终回答合同正确率 100%、端到端任务成功率 99.25%，P95 端到端延迟 6.65 秒。

**面试口语：** Agent 的问题不在于让模型回答得更长，而在于业务合同必须闭环。此前空知识会被当成成功，阻断与确认也可能混在一起，跨领域任务在一个分支失败后还会过早结束。我把空来源改成 fail-closed，让知识检索按当前 Case 隔离，并让 Supervisor 只按冻结 DAG 调度独立步骤。然后用 100 个 WorldState、400 条表达跑真实模型全链路，最终回答合同正确率达到 100%，端到端任务成功率 99.25%，P95 约 6.65 秒；这代表冻结业务 Gold 下的工程可靠性，不代表临床准确率。

## 6. 面试口述

> 我做的是互联网医院慢病续方和家庭用药场景。这个业务不是让模型自由聊天，而是同一个请求可能同时涉及处方、药箱、报告、知识规则和人工确认。我的方案是简单请求直达领域 Agent，复杂请求只规划一次，再由 Supervisor 按冻结依赖调度。Agent 不能直接访问数据库，只能通过统一工具调用层获取同一成员的事实；安全、确认、Checkpoint 和事后评测都是固定节点。PostgreSQL 保存权威状态，Redis 只做短期缓存，所以缓存失效后仍能恢复，并通过新 run 完成确认续跑。
>
> RAG 的第一类问题是规则编号、药品名这类精确实体会被语义相近片段挤出前排，所以我在活动版本内并行 BM25 和 HNSW 向量召回，用 RRF 融合，再做实体过滤和候选 20 条规则重排，Recall@3/@5 从 67.50%/85.19% 提升到 100%/100%。第二类问题是多片段题虽然召回了同一文档，却没有区分步骤和例外，模型会合理拒答。我给 Query 和 Chunk 增加证据角色约束，每个角色只选择一个直接来源，并让答案先回答用户所问内容。最终 320 条 RAG Query 的来源绑定回答正确率从 74.69% 提升到 99.69%，260 条可回答题的 Faithfulness 和 Response Relevancy 为 0.9837 和 0.6818；这些都是合成工程指标，不代表临床效果。

## 7. 事实边界

- 后续新增或复测的所有指标统一使用 `internet-hospital-agent-eval-v1` 的 fast-400 活动视图；当前活动视图包含 225 个基础状态和 900 条合成 Query（Agent 400 + RAG 500）。完整 Agent 300/1200 来源只用于历史追溯，不能混入新的简历指标。

- 数据不是患者数据或临床 Gold，指标不是临床准确率、线上成功率或生产 SLA。
- 尚未接入真实医院、药店、支付和通知生产系统。
- 当前 RAGAS Judge 已完成 260 条可回答题最终复评并全部三项齐全；60 条无答案题单列无答案准确率 100%。Faithfulness/Response Relevancy/Context Recall 为 0.9837/0.6818/1.0000；仍需明确是自动合成、无人工审核的工程指标。Precision@K 不能把稀疏 Gold 的固定分母上限误判成 rerank 质量差。

## 8. 报告闭环与质量控制表达

**简历一句话：** 实现医疗报告的文本、Markdown 表格、PDF 文本层与本地 OCR 统一解析，将章节、表格和结构化指标直接沉淀为成员作用域内的可读契约；在最终输出前增加无工具质量门，安全或无来源事实直接阻断、格式问题最多一次受限修复，并复用 PostgreSQL Checkpoint 保留可追溯审计。

**面试口述：** 报告场景最容易把“提取到的指标”误写成“诊断结论”。我把解析层限制为统一的来源结构和可读指标，上传后直接用于展示，但不自动写健康事件、更不推导诊断或治疗。回答生成后先走 Agent 安全，再走最终回答质量门：它只检查确认提示、来源和展示完整性，不能再调工具或重规划。这样既避免把一次模型输出当成医疗结论，也保证缓存失效时可从 PostgreSQL 恢复审计链路。
