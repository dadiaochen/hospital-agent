# 后端与大模型应用开发面经问答

> 当前最终口径：三个领域 Agent，简单请求直达，复杂请求使用一次性 Planner + 串行 bounded Supervisor；三层安全由状态图强制执行；PostgreSQL 保存权威 checkpoint/确认/偏好，Redis 只做 TTL 缓存并可回源；医疗知识使用独立 pgvector RAG。项目不实现 MCP Server、Agent 级并行、OpenTelemetry/Jaeger 或复杂自动重规划。旧问答若描述早期角色或确认流程，应作为演进背景，不得覆盖此口径。

这份文档根据近期面试题和项目当前路线整理。回答默认遵循：先给结论，再讲设计、取舍、项目证据和边界。

> **面试术语规则：** 本文优先使用面试官实际会说的业务和工程术语。涉及安全、评测、检索和 Agent 协同时，先用自然的面试表达，再补充必要的实现细节；不把代码类名、内部模块名或直译词直接当成面试术语。本文统一使用“Agent 安全”和“Agent 评测”。

### Q2：你负责的 Agent 系统技术栈和架构是什么？

**参考回答：**

我会先讲架构，不会一上来报框架名。后端分成接口层、业务层、数据访问层、Agent 编排、工具调用、RAG 和 Agent 安全几个部分。Agent 编排先识别用户要处理哪个家庭成员、要完成什么任务、还缺哪些信息；不同处理角色只拿到自己需要的最小上下文，不能看到其他成员的处方和病史。所有档案、处方、药箱、库存和知识规则都必须通过统一的工具调用层读取，不能让模型直接访问数据库。

工具调用前会检查参数格式、权限、家庭成员范围和是否需要用户确认，调用后记录输入、输出、耗时和失败原因。最终回答生成前还要做结构化输出检查和 Agent 安全检查。回答完成后保留运行轨迹和任务摘要，再由 Agent 评测只读检查任务是否完成、资料是否有来源、是否串成员以及是否遗漏用户确认。面试官继续追问时，我再展开具体使用的后端框架、数据库和 LangGraph。

### Q3：Agent 和传统工作流有什么本质区别？

**参考回答：**

传统工作流通常由代码预先决定路径和参数；Agent 可以根据用户目标、当前状态和工具结果选择下一步，更适合信息不完整、需要补充提问或需要动态选择工具的场景。

但医疗场景不能把自主性理解成无限自由，所以项目采用“有边界的自主执行”。模型只负责理解任务和整理信息，任务路由、最大执行次数、允许调用的工具、Agent 安全和用户确认都由程序控制。这样既保留 Agent 处理自然语言和动态任务的能力，也避免它自行开方、改药或跳过确认。

### Q4：多 Agent 协同怎样做状态同步？

**参考回答：**

我不会把完整聊天历史广播给所有 Agent，而是先整理成一份结构化运行上下文，里面只保留当前家庭成员、当前任务、已确认信息、缺失信息、工具结果、RAG 来源、安全标记和允许调用的工具。

每个角色只接收职责需要的内容：档案查询只看成员档案，药店查询只看药品和库存条件，Agent 安全只看风险信息和待执行动作。角色之间共享的是已经确认的事实、工具结果和来源编号，不共享各自的临时推理内容。这样可以减少上下文污染，也能防止父亲和母亲的信息串在一起。

### Q5：中心化状态管理有性能瓶颈时会考虑 CRDT 吗？

**参考回答：**

会先判断问题类型。当前项目的主要耗时更可能来自模型、检索和工具调用，不是多人协同编辑，所以优先做状态分区、短期缓存、异步 IO 和按角色读取，不会为了多 Agent 直接引入 CRDT。

如果以后出现离线更新、多写入方和高频合并，再评估 CRDT 或事件溯源。提醒偏好这类可合并数据可以考虑 CRDT；处方状态、人工确认和医疗草稿更适合带版本号的事务更新，不能用无条件合并掩盖冲突。

### Q6：Agent 开发最重要的是什么？

**参考回答：**

我会把可评测、可观测、可控放在单纯追求模型聪明之前。Agent 不只要回答得自然，还要知道用了哪些工具、依据来自哪里、是否串成员、是否绕过确认、失败后如何处理。

所以项目先准备固定用例，记录完整运行轨迹，再从任务完成、工具调用、资料来源、Agent 安全、用户确认和成员隔离几个维度做 Agent 评测。固定输入、固定输出的本地测试可以先验证流程和失败分类，但它不等于真实模型质量，更不能被表述成临床安全证明。

### Q7：如果模块化输入导致 Agent 对整体需求理解不足，怎么办？

**参考回答：**

模块化不等于把需求切碎后互不沟通。编排层先形成完整任务目标，明确要处理哪个家庭成员、缺什么信息、需要哪些工具；之后各角色在隔离的上下文中执行，只把结构化结果和资料来源回传。每个模块都要明确输入、输出、约束和失败方式，最后由编排层汇总，而不是依赖模型自行猜模块之间的关系。

### Q8：为什么不把整个文档直接塞给模型？

**参考回答：**

内容过多会增加 Token 消耗和延迟，也会稀释模型注意力，把不同成员或不同任务混在一起。应先按任务、家庭成员、安全等级和资料来源过滤，再进行关键词检索或向量检索，必要时做重排，最后只把当前角色需要的最小证据放进上下文。

## 2. Coding Agent 与软件工程

### Q9：你用过哪些 Coding Agent？

**待本人确认后补全：**

这道题需要确认本人实际使用过哪些 Coding Agent、各自使用到什么深度以及完成过什么任务。确认前保留题目，不编写通用答案，也不把“了解过”写成“实际使用过”。

### Q10：Cursor 和 Claude Code 分别适合什么任务？

**参考回答：**

比较时不只说“效果差不多”，而是看代码库索引、上下文获取、命令执行和权限模型、长任务恢复、规则文件、diff 审查、测试闭环、成本和团队协作。对本项目来说，工具能否遵守 `AGENTS.md`、阶段边界和验证要求，比单次生成速度更重要。

### Q11：Coding Agent 的 skill 有什么价值？

**参考回答：**

Skill 可以把重复流程沉淀成可复用的规则和工具，例如需求澄清、Git 最佳实践、测试检查或文档生成。它应该固定输入、输出、允许操作和验收条件，而不是给 Agent 无限权限。医疗安全检查仍由代码规则和统一工具入口兜底。

### Q12：你了解 spec-driven development 吗？

**参考回答：**

了解。它强调先定义需求、契约、状态和验收，再让 Agent 生成实现。优点是减少上下文歧义，缺点是前期文档成本更高。跨模块或高风险任务适合使用“需求文档 + 设计契约 + 实现计划 + 测试”，小修复则保持轻量。

### Q13：上下文压缩怎么做？

**参考回答：**

保留当前任务相关的事实、还缺的信息、工具结果、RAG 来源和安全标记，把旧对话压成结构化摘要，而不是简单截断。摘要要注明信息来自哪份资料、属于哪位家庭成员，不能把模型猜测写成已经确认的事实。

Coding Agent 常见的做法是保留较近的一部分对话，让模型把更早内容压缩成结构化摘要。压缩比例要由 token 预算、任务重要性、摘要质量和成本共同决定；需求、错误上下文和安全规则不能因为较早就无条件丢弃。

### Q14：OpenClaw 的 memory search / memory get 怎么理解？

**参考回答：**

可以抽象成两步：`memory_search` 先检索相关 memory 文件，返回候选内容、路径和位置；`memory_get` 再按需读取具体内容。这样比每轮把所有长期记忆塞给模型更省上下文，也更容易审计。不了解具体实现时要明确说是抽象理解，不要补造细节。

### Q15：未来软件工程会不会变成只给 Agent 提需求？

**参考回答：**

代码生产会越来越自动化，但软件工程不等于写代码本身，还包括需求澄清、系统设计、接口契约、测试、部署、维护、成本和风险控制。工程师的价值会更多转向定义约束、验证结果和处理复杂异常。AI 生成的代码仍然需要人理解、审查和承担后果。

## 3. RAG 与幻觉控制

### Q16：Embedding 是什么？

**参考回答：**

Embedding 是把文本映射成向量，使语义相近的内容在向量空间里更接近。检索时可以计算余弦相似度或使用向量数据库做近邻搜索。它解决的是语义召回，不等于事实判断，也不能替代权限过滤、成员隔离和安全规则。

### Q17：为什么需要 rerank？

**参考回答：**

第一阶段召回通常追求覆盖率，候选较多且排序不够精细。Reranker 对 query 和候选文档做更细粒度的相关性判断，提升 Top-K 精度。常见架构是“便宜的召回 + 更精确的 rerank”，而不是让大模型对无限候选直接排序。

### Q18：能不能直接让大模型判断哪些内容最相关？

**参考回答：**

可以作为受限的 rerank 或解释步骤，但不适合做唯一检索控制面。它成本高、延迟不稳定、结果难复现，还可能把相关但不安全的内容排在前面。应先做确定性过滤和召回，再按安全等级、来源和任务约束排序，模型只处理有限候选。

### Q19：你的系统如何降低大模型幻觉？

**参考回答：**

第一，事实必须来自数据库、外部接口或能够回溯原文的 RAG 结果；第二，模型输出要做格式校验和 Agent 安全检查；第三，缺少证据时明确说“现有信息不足”，必要时转人工，而不是让模型自行补全。

历史处方、药箱余额、库存和家庭成员都不能来自模型记忆。模型只能解释结构化证据，不能凭空生成医疗建议。

## 4. AI/Agent 项目深挖

### Q20：从用户输入到最终回答，项目的完整链路是什么？

**参考回答：**

用户请求进来后，先校验身份和当前操作的家庭成员，再判断用户是在问续方、复诊材料、用药提醒，还是高风险用药问题。如果信息不够就先追问，不急着调用工具。

信息完整后，系统只把当前任务需要的内容交给对应的 Agent，再通过统一工具入口查询成员档案、历史处方、药箱、药店库存和知识库。所有查询结果都保留来源。涉及停药、加量、换药或其他高风险内容时，要在生成答案和待确认内容之前经过 Agent 安全检查。最后再校验回答格式，记录本次运行过程，生成任务摘要，并在任务结束后做 Agent 评测。

口头回答最后要补一句真实进度：目前已经验证了本地工作流和接口链路，真实模型、医院和药店接口仍需要后续接入，不能把设计方案说成已经在线上运行。

### Q21：为什么选择 LangGraph？是自研 Agent，还是固定工作流？

**参考回答：**

LangGraph 适合这种有明确状态、条件分支、工具调用和人工确认的任务。自己写编排也能实现，但状态保存、异常恢复、运行记录和流程维护都要重新做一套。

这个项目本质上是有边界的 Agent 工作流：模型可以做意图识别和有限决策，但最大步骤、可用工具、人工确认点和结束条件由程序控制，不允许无限循环。选择 LangGraph 是因为它能把这些状态和分支表达清楚，不是单纯因为框架流行。

### Q22：单 Agent 和多 Agent 怎么选择？子 Agent 分别负责什么？

**参考回答：**

我先用单 Agent 验证完整流程，只有当职责、工具权限或上下文边界明显不同才拆分。最终业务层只保留三个领域 Agent：`TriageAgent` 负责预问诊信息结构化，`MedicationAgent` 负责处方/药箱/库存/提醒草稿，`ReportAgent` 负责医疗文档结构化和有来源解释。简单任务由 Complexity Router 直达一个领域 Agent；跨领域任务才由一次性 Planner 拆成最多三步，再由串行 bounded Supervisor 按依赖执行。

每个角色都要说清楚负责什么、能看什么信息、能调用什么工具、失败后怎么处理。只是复制几份 Prompt、换几个角色名，不算真正的多 Agent。Planner 只决定“要完成什么”，Supervisor 只决定“冻结计划中的下一步由谁执行”，两者不会同时改写任务目标。

本项目的 Agent 安全负责运行时拦截，Agent 评测负责答案生成后的只读评估，两者不能混用。

为了避免只讲架构名词，我做了 32 条 deterministic fixture 的同条件消融：三组共享模型身份、工具目录、RAG、安全、确认和 token 上限。固定路由在 26 条简单任务上完成率为 1.0000，说明简单任务没必要进入 Supervisor；在 6 条复杂任务上为 0.0000，因为只进入主领域会漏掉第二领域工具。bounded Supervisor 在复杂任务上为 1.0000，工具集合/参数 exact-match 也是 1.0000；Single-Agent 虽然完成率为 1.0000，但工具 exact-match 只有 0.3750，并存在重复调用。这些数字只能称为固定 deterministic 回归结果，不能说成线上准确率或临床效果。

### Q23：首次生成和多轮补充的链路如何区分？

**参考回答：**

第一次请求会建立一条新任务，记录用户目标和还缺哪些信息。用户后续补充时，系统读取上一轮的任务摘要和来源记录，更新已经确认的信息，只执行仍然缺失的步骤。

不能把上一轮完整对话和模型内部推理直接交给所有 Agent，也不能因为用户补充了一句话就把整个流程重跑。这样既减少 Token 消耗，也能降低家庭成员信息串用和重复调用工具的风险。

### Q24：基座模型如何选择？为什么考虑或不考虑微调？

**参考回答：**

先看任务质量、结构化输出稳定性、上下文长度、延迟、成本、部署方式、隐私和工具调用能力，再用固定用例做横向比较。稳定的领域格式和大量高质量标注数据才适合考虑微调；如果主要问题是事实来源、权限或流程控制，优先做 RAG、工具约束和输出校验，而不是直接微调。

如果项目当前没有真实微调或线上模型评测，应明确说“做过方案分析或接口预留”，不能虚构训练数据、模型版本和提升比例。

### Q25：Prompt 模板如何设计和迭代？如何让模型更聚焦？

**参考回答：**

Prompt 要分别说明角色边界、任务目标、可用信息、证据来源、输出格式、禁止事项和失败处理，并通过版本管理和固定评测集验证修改效果。复杂任务可以给模型一份步骤清单，让它知道当前做到哪一步，但步骤数量和可执行动作仍然由程序限制。

Prompt 优化不能只挑一条看起来更漂亮的答案，要看 badcase、输出格式通过率、工具调用准确率、来源引用和安全拦截有没有整体改善。

### Q26：查询改写、补充信息和多路召回怎么设计？

**参考回答：**

查询改写只能补充表达，不能改变用户原意，更不能凭空增加医疗事实。系统要同时保留用户原问题、改写后的问题、对应的家庭成员和信息来源。缺少关键信息时，应直接向用户追问，而不是让模型猜。

多路召回可以组合关键词、结构化过滤和向量召回，再统一去重、排序和来源校验。第二次检索要有明确的触发原因和质量检查，不能为了“多搜一次”而无限循环。

### Q27：工具字段是英文或模型经常传错参数，如何处理？MCP 有什么作用？

**参考回答：**

工具不直接接收任意自然语言，而是通过统一工具注册层定义工具名称、用途、输入参数、返回格式、权限、超时、重试和是否需要用户确认。外部接口字段是英文时，由参数映射和数据校验层处理，不把字段含义交给模型猜。

这个项目借鉴了 MCP 的标准化思路，让工具能力、权限和调用方式保持一致，但目前不是完整的 MCP Server。MCP 也不能替代业务权限和 Agent 安全校验，更不意味着所有内部接口都应该暴露给 Agent。

### Q28：RAG 的文档预处理和切分怎么做？

**参考回答：**

先按 PDF、表格和图片 OCR 等来源做解析、清洗和结构恢复，保留文档名称、页码、表格关系、版本和权限信息，再切分成可以回溯原文的内容片段。固定长度切分实现简单，但可能破坏语义；按标题、段落、表格和语义边界切分更适合知识库，但需要处理过长段落和跨页引用。

切分结果必须能回溯原文，不能只把一段脱离上下文的向量写进库后让模型自行补齐。

### Q29：为什么需要向量数据库？为什么不直接用 MySQL？

**参考回答：**

MySQL 或 PostgreSQL 负责权威结构化数据、权限和事务；向量索引解决语义近邻召回，两者不是互相替代。小规模场景可以先用关键词或数据库扩展做基线，规模和召回需求上升后再引入 pgvector 或其他向量后端。

项目要说明实际使用的数据库、Embedding 模型和索引；如果只是接口设计或 mock，就不能声称已经完成真实向量检索。

### Q30：如何评估 RAG 效果？召回率大概是多少？

**参考回答：**

检索层可以评估 Recall@K、Precision@K、MRR 或 nDCG；答案层要看回答是否有来源支撑、引用是否正确、该拒答或转人工时是否处理正确、输出格式、延迟和成本。评测要使用固定问题集、人工标注来源、重复运行和 badcase 回归，不能凭主观感受报一个召回率。

没有真实评测集和运行记录时，只能说指标定义或目标，不能把设计值写成已经达到的结果。

### Q31：短期记忆、长期记忆和上下文压缩怎么做？

**参考回答：**

单次运行的短期状态放在 LangGraph Working State，只保留当前任务必要的摘要、缺失信息和来源指针；run 结束就清理。跨 run 的 Task Checkpoint、确认记录和用户明确确认的偏好由 PostgreSQL 权威保存，Redis 只做带 TTL 的短期缓存并在故障时回源 PostgreSQL。草稿是业务状态，不叫长期记忆；处方、报告和药箱等医疗事实每次从业务数据库或 Provider 重读。

压缩时要保留任务编号、家庭成员、信息来源、安全标记和未完成事项，清理无关历史与临时推理。未经用户确认的模型推断不能写入长期记忆。

### Q32：Agent 执行模式如何选择？如何防止死循环？

**参考回答：**

ReAct 适合边观察边调用工具，Plan-and-Execute 适合先拆计划再执行，Reflection 适合在结果后做受限检查。医疗业务更适合由 intent 驱动的有界 DAG，明确最大步骤数、允许工具、终止条件和失败降级。

无论使用哪种模式，都要记录每一步状态和工具证据，不能让模型自行决定无限重试或绕过确认。

### Q33：如何测试多模态模型和 Prompt Injection 安全？

**参考回答：**

先定义输入、输出和工具权限边界，再覆盖文本、图片、恶意指令、间接提示词注入、越权读取、敏感信息泄露和高风险动作等用例。模型输出要经过规则检查和格式校验，工具调用还要经过权限与 Agent 安全检查；遇到危险请求应拒答、降级或转人工。

“奶奶漏洞”这类题目不能只回答一句过滤关键词，要说明攻击样本集、策略分层、误报漏报评估、日志审计和回归机制。

### Q34：SFT、提示词工程和 Agentic RL 怎么取舍？

**参考回答：**

先定位问题属于知识缺失、格式不稳、工具规划错误还是奖励目标不清。知识和事实优先用 RAG，格式和行为稳定性可以考虑高质量 SFT；涉及复杂轨迹或奖励优化时再评估更复杂的训练方案，并保留独立验证集和安全回归集。

训练数据要说明来源、脱敏、格式、质量过滤、训练/验证划分和评测口径。没有真实训练经历时，只讲理解和方案，不把论文或教程看过说成已经落地。

### Q35：如何降低模型延迟？流式、非流式、KV Cache 和批处理怎么选？

**参考回答：**

先拆分模型、检索、数据库、工具和序列化耗时，分别看 p50/p95。交互场景可以使用流式输出改善首 token 体验；需要完整 JSON 或严格确认时仍可能使用非流式。KV Cache、连续批处理和 vLLM 属于推理优化手段，必须结合显存、并发、吞吐和一致性验证，不能只背名词。

模型 API 的 `temperature`、`top_p` 会影响采样分布，但 temperature 为 0 也不代表不同模型服务的输出一定完全相同。模型服务、模型名称、超时和密钥必须由服务端配置控制。

### Q36：如何设计 Agent Harness 和 badcase 闭环？

**参考回答：**

先固定评测用例，明确输入、家庭成员、允许调用的工具和预期安全结果，再保留完整运行轨迹。评测时看任务是否完成、工具是否调用正确、回答是否有来源、输出格式是否正确、高风险问题是否拦截、用户确认是否完整，以及家庭成员信息是否隔离。

badcase 要保留原始输入、执行过程、工具结果和失败分类，修复后回放同一用例。Agent Harness 能证明工作流和回归结果稳定，但不能直接证明真实模型质量，更不能把它说成临床安全证明。

### Q37：如何定位 Agent 项目的问题？如何关联日志、告警和工具调用？

**参考回答：**

每次请求都用统一的运行编号、任务编号和家庭成员编号，关联接口、模型、RAG、工具调用、错误和最终答案。定位时从用户看到的现象开始，按时间线查看工作流走到哪一步、工具输入输出是什么、信息来源在哪里、有没有重试或降级，再区分数据、模型、编排、外部依赖和展示问题。

日志要结构化并脱敏，告警不能只看一条异常文本；要结合错误率、延迟、工具失败率、来源缺失和成员隔离失败等指标判断根因。

### Q38：如何回答 OpenClaw、Claude Code、Codex 等工具问题？

**参考回答：**

只描述自己真实使用或阅读过的范围，区分 Coding Agent 和业务 Agent。可以比较上下文获取、规则文件、命令权限、skill/tool、长任务恢复、diff 审查、成本和测试闭环，但不能凭概念编造某个工具的底层实现。

本项目中 Coding Agent 主要用于需求澄清、分阶段修改、测试和文档；业务 Agent 则负责受限的家庭健康事务流程，两者的权限模型和验收标准不同。

### Q39：如何把 AI 生成代码、单测和 Agent 评测串成工程闭环？

**参考回答：**

AI 可以根据 AST、调用关系和接口约定生成测试候选，但不能直接充当正确答案。工程师要先定义边界、异常、mock 范围和断言，再运行代码格式检查、静态检查、单元测试、集成测试和必要的变异测试；Agent Harness 记录生成输入、工具调用、测试结果、失败原因和回归用例。

覆盖率高不代表测试质量高，还要看断言有效性、缺陷检测率、flaky 率和关键路径。模型生成的代码与测试都必须经过人工 review，并且可以回滚。

### Q40：Agent 评测做什么？和 Agent 安全有什么区别？

**参考回答：**

两者介入时机不同。Agent 安全是在运行过程中拦截风险，比如用户要求停药、加量、换药，或者试图查看其他家庭成员的信息；Agent 评测是在一次任务结束后复盘这次执行是否正确。

Agent 评测会看任务是否完成、工具是否调用正确、回答有没有来源、是否遗漏用户确认、家庭成员信息有没有串用，以及耗时和失败原因。它只读运行记录，不修改用户答案，也不参与实际业务执行。

## 5. 实习、岗位与场景追问

### Q41：如果入职，你作为实习生会先做什么？

**参考回答：**

先了解业务目标、代码仓库、部署方式、日志和验收标准，再从一个边界清晰的小任务开始，补测试、记录验证证据并主动同步风险。遇到不确定的技术问题先复现和查资料，再带着上下文向 mentor 提问，而不是只等待分配。

### Q42：你的优势和需要补齐的地方是什么？

**参考回答：**

优势要落到证据，例如能把 Agent 需求拆成状态、工具、来源和失败路径；需要补齐的地方要给出行动计划，例如深入推理优化、真实线上观测或某个基础设施。不要用“我什么都会”或“代码以后都由 AI 写”作为回答。

### Q43：如果让你做一个带 TUI 的视频剪辑 MVP，怎么设计？

**参考回答：**

先收敛 MVP：素材导入、时间线、裁剪、预览、导出和错误恢复。分层可以包括 TUI 交互层、领域状态层、媒体处理适配层、任务队列和持久化层；长任务异步执行，展示进度、取消和失败原因。回答团队分工时要明确自己负责的边界、里程碑、阻塞处理和验收标准。

### Q44：为什么离开上一段经历，下一份工作最看重什么？

**参考回答：**

围绕工作内容、成长方向和岗位匹配回答，不评价个人或团队。可以说希望继续做后端与大模型应用工程，接触真实业务约束、评测和上线闭环；同时说明地点、到岗时间和实习周期等客观信息。

### Q45：你会向面试官反问什么？

**参考回答：**

可以问岗位当前最重要的业务问题、Agent/后端团队的职责边界、评测和上线标准、实习生的交付方式、代码 review 与 mentor 机制，以及后续面试重点。问题要体现你关心如何交付，而不是只问福利和技术名词。

## 6. 图片补充：Agent 工程高频追问

### Q46：什么是 Agent Harness？一个最小的 Agent 循环包括什么？

**参考回答：**

Agent Harness 可以理解为包在大模型外面的运行框架。大模型负责理解和生成，Harness 负责把一次任务真正跑起来，包括上下文管理、工具调用、状态保存、权限控制、运行记录、失败恢复和评测。

一个最小循环是：理解当前任务，判断是否需要调用工具，执行工具并读取结果，再决定继续还是结束。工程上还要限制最大轮数、超时、Token 和工具调用次数，避免死循环和成本失控。这个项目采用的是有边界的状态流，不让模型无限自主循环。

### Q47：Tool Calling、MCP 和 Skill 有什么区别？

**参考回答：**

Tool Calling 是模型决定调用哪个函数，并生成函数名和参数；MCP 是把工具发现、连接和调用方式标准化的协议；Skill 更像一个完整业务能力的封装，里面可以包含提示词、多个工具、执行步骤和异常处理。

三者不是互斥关系。一个 Skill 内部可以通过 Tool Calling 调用工具，也可以接入 MCP 提供的工具。这个项目目前做的是类似 MCP 的工具注册和调用规范，还不能说已经实现了完整的 MCP Server。

### Q48：Run Trace、checkpoint 和任务恢复分别解决什么问题？

**参考回答：**

Run Trace 是一次 Agent 执行的完整运行轨迹，记录每一步做了什么、调用了什么工具、结果来自哪里、哪里失败以及用了多长时间，主要用于排错、审计和评测。

checkpoint 保存的是可以继续执行的任务状态。当前项目已实现任务八：首次 run 把 RunSummary、步骤进度、确认状态、冻结产物和来源指针写入 PostgreSQL 权威 checkpoint；确认时在同一 task 下创建新的 continuation run，通过 `parent_run_id`、checkpoint/confirmation version 和幂等键避免陈旧确认或重复执行。Redis 只做带 user/member/task/thread/version 作用域的 TTL 缓存，miss 或故障回源 PostgreSQL。恢复时不带回 scratchpad、完整对话或未确认推断，而是重新读取处方、库存和报告等可变业务事实。流式回答如果中断，也不能凭空补齐丢失的 Token。

### Q49：Agentic RAG 和普通 RAG 有什么区别？

**参考回答：**

普通 RAG 的流程通常是固定的：检索、拼接上下文、生成答案。Agentic RAG 会让 Agent 根据问题决定要不要检索、检索什么、是否改写查询、要不要补充检索和重排。

它更适合复杂问题，但也会增加延迟、成本和不稳定性，所以不能为了“更像 Agent”就全部改成自由循环。这个项目更适合有边界的 Agentic RAG：可选择检索路径，但轮数、工具和终止条件由程序限制。

### Q50：长文档、表格和图片进入 RAG 前怎么处理？

**参考回答：**

我会先保留文档结构，再做内容切分。标题层级、段落、表格表头、页码和图片说明都要保留，不能只把所有文字连成一段。扫描件先做 OCR，表格按表头和行列关系单独处理，图片则保存说明和所在章节。

检索时可以结合关键词检索和向量检索，再做重排，并为每个片段保留来源编号。标题缺失或 OCR 位置不准时，可以结合编号、字体、相邻段落和版面位置判断；低置信度内容进入人工复核，不能为了回答完整而猜测。

### Q51：Prefix Caching 是什么？怎么避免缓存污染？

**参考回答：**

Prefix Caching 是复用重复前缀已经计算过的缓存，适合系统提示词、固定工具说明等稳定内容，可以减少重复计算。缓存键至少要包含模型版本、分词器、系统提示词、工具定义和安全策略版本。

用户问题、家庭成员资料、处方和库存属于动态且敏感的数据，不应放进跨用户共享的前缀缓存。任何关键配置变化都要让缓存失效，并配合过期时间、容量淘汰和用户隔离，避免旧规则或其他成员信息被复用。

### Q52：用大模型做评测会不会有偏差？评测集怎么设计？

**参考回答：**

会有偏差，尤其是同一家模型评价自己的输出时，可能偏好相似的表达方式。所以不能只依赖一个大模型打分，要把规则校验、人工标注和大模型评测组合起来；做版本对比时还可以隐藏答案来源、交换答案顺序，并抽样与人工结果校准。

评测集要覆盖正常任务、边界问题、工具异常、无来源回答、提示词注入、高风险医疗请求和家庭成员信息串用。AI 可以帮助扩充用例，但关键预期结果必须人工审核，不能让模型自己出题、自己作答、再自己判分。

### Q53：Skill 怎么动态加载？如何保证输出稳定？

**参考回答：**

可以先只加载 Skill 的名称、用途和权限，确定要使用后再加载完整提示词和执行步骤，这就是渐进式加载。这样能减少上下文长度，也避免把无关能力全部交给模型。

稳定性主要靠程序约束：Skill 要有版本、输入输出格式、允许调用的工具、超时、重试和结果校验；上线前用固定用例回归。模型可以在允许范围内选择参数，但不能自由改写业务规则或绕过用户确认。

### Q54：如果让你设计一个 Agent API 或 Agent 管理平台，会怎么分层？

**参考回答：**

我会分成接入层、任务运行层、模型与工具层、知识和记忆层、运行记录与评测层。接入层负责身份、权限和限流；任务运行层管理任务状态、取消、超时和流式输出；模型与工具层统一处理模型调用、工具注册和失败降级；最后用运行轨迹支撑排错和评测。

模型地址、密钥和超时只能由服务端配置，不能让请求参数或提示词覆盖。这个项目实现的是业务 Agent 的基础能力，还不是完整的通用 Agent 平台。

### Q55：Agent 安全怎么做？敏感信息怎么保护？

**参考回答：**

Agent 安全不能只靠一句提示词。像诊断、停药、加量、换药、严重症状、跳过用户确认和跨家庭成员查询，先用明确规则拦截；模型可以辅助识别表达变体，但不能单独决定高风险动作。

数据侧要做最小权限、成员隔离、敏感信息脱敏和完整审计。外部文档和工具返回也要防提示词注入，模型看到的内容只作为资料，不能覆盖系统规则。复诊、购药和提醒创建都必须先生成待确认内容，由用户确认后再继续。

### Q56：Agent 上线后看哪些稳定性指标？

**参考回答：**

我会同时看业务正确性和系统稳定性。前者包括任务完成率、工具调用准确率、回答来源完整性、高风险拦截率、用户确认完整性和成员隔离；后者包括响应时间、Token 消耗、模型和工具失败率、重试次数、队列积压和降级次数。

每次执行用任务编号串起日志、工具调用和评测结果，再配合超时、熔断、幂等、灰度和回滚。当前项目能验证本地流程和固定用例，没有真实线上数据的指标只能说是设计目标。

### Q57：用户在多轮对话中补充信息，Agent 怎么继续执行？

**参考回答：**

先判断是不是同一个任务。如果是同一个任务，就基于上一轮的任务摘要和来源继续，只更新用户明确确认的信息，并只执行仍然缺少的步骤；如果切换了家庭成员或目标，就重新建立隔离的上下文。

缺少关键资料时要明确追问，不能把模型猜测当成事实。无关问题可以创建新任务，不能把两件事的历史、处方或库存混在同一个上下文里。

### Q58：上下文达到上限，但任务还没有完成，怎么办？

**参考回答：**

我不会直接截掉最早的消息继续跑，而是先区分哪些信息必须保留：当前目标、用户已确认的事实、还缺什么、工具查到的结果、资料来源和安全标记。旧对话压缩成任务摘要，工具结果和引用单独保存，下一轮从摘要和来源继续。

如果压缩后仍然无法安全完成，就明确告诉用户需要补充信息或继续下一轮，不能把被截断的内容当成已经处理。程序还要限制最大步骤、最大工具调用次数和最大 Token，防止任务在上下文不足时无限循环。

### Q59：多 Agent 之间怎样传递成功、失败、超时和重试状态？

**参考回答：**

子 Agent 返回的不是一大段思考过程，而是一份结构化任务结果，至少说明执行状态、得到的结果、来源、失败类型以及是否适合重试。主 Agent 只接收完成后需要继续决策的信息，不共享各自的临时推理内容。

重试次数、超时和降级路径由程序控制，不能让模型自己无限重试。涉及创建草稿的步骤还要做幂等，同一任务重复执行时返回原结果，避免因为网络超时重复创建。

### Q60：高风险拦截闭环怎么证明真的执行成功？

**参考回答：**

我会从三层验证。第一层是输入高风险用例后确实命中拦截；第二层是运行轨迹显示拦截发生在生成草稿或执行动作之前；第三层是数据库和任务状态里没有产生本不该产生的购药、复诊或提醒草稿。

同时检查用户看到的回答是否明确说明不能自行停药、加量、减量或换药，并引导咨询医生。固定用例可以重复回放，但这些结果只能证明软件流程符合规则，不能说成已经证明临床安全。

### Q61：长文档的 OCR 和版面结构怎么评测？

**参考回答：**

不能只看文字识别准确率，还要看标题层级、段落顺序、表格行列、页码和图片说明有没有保留下来。对扫描件、双栏文档、复杂表格和标题缺失等版式分别建立人工标注样本，再检查文字、位置、层级和来源页是否正确。

如果使用 MinerU 或其他文档解析工具，我会先说明是已经接入、做过对比，还是只是技术选型。没有实际测试数据时，只讲评测方案，不编造识别率。

### Q62：模型调用层怎么设计，才能切换模型而不影响业务？

**参考回答：**

业务层只依赖固定的输入输出格式，不直接写死某一家模型的接口。模型调用层负责读取服务端配置、调用不同模型、处理超时和重试，并统一做结构化输出校验和安全检查。

切换主模型或备用模型时，两者必须遵守同一份输出约定；备用模型的结果也要重新校验，不能因为降级就绕过规则。模型地址、密钥和名称只能由服务端配置，不能让用户请求或提示词修改。

### Q63：流式输出中断或用户刷新页面，怎么恢复？

**参考回答：**

开始流式输出前先保存任务和消息记录，每个输出片段带递增序号。连接中断后，客户端用任务编号和最后收到的序号重新连接，服务端从已保存的位置继续发送；如果模型本身不支持续写，就把这次输出标记为中断，并基于已保存的任务重新生成，不能假装无缝接上。

只有完整通过校验的答案才标记为最终结果。工具调用和草稿创建要做幂等，页面刷新不能重复执行关键动作。当前项目已具备任务记录思路，流式断点续传仍属于后续可以补充的能力。

### Q64：项目上线了吗？有多少用户？准确率是多少？

**参考回答：**

我会直接说明项目当前处于本地开发和测试阶段，没有真实医院用户，也没有生产环境准确率。已经完成的是项目骨架、数据模型、业务流程和一部分固定用例验证；仍在推进的是完整场景联调和更系统的 Agent 评测。

面试时要把“已经测出来的结果”和“准备采用的指标”分开。没有数据就说没有，并补充准备怎样测，比给一个无法解释样本范围的百分比更可信。

### Q65：Coze、Dify、n8n 和自研 Agent 框架怎么选？

**参考回答：**

Coze、Dify 和 n8n 更适合快速搭建流程、连接现成服务和验证产品想法；自研框架成本更高，但对状态、权限、数据隔离、运行轨迹、版本和评测的控制更细。

这个互联网医院项目涉及家庭成员隔离、医疗高风险拦截和用户确认，所以核心流程更适合自己控制。可以用低代码工具验证外围流程，但不能只因为工具热门就全部自研，也不能没有实际使用就声称熟悉其内部实现。

### Q66：你自己这个 Coze 编排的 pipeline 是什么？工作流具体怎么连？

**参考回答（口头版）：**

我实习中实际用的是 Dify，不是 Coze，不过这类可视化工作流的编排思路是相通的。如果把互联网医院这个项目放到 Dify 里，我不会做成一个自由对话机器人，而会做成一条有明确分支和结束条件的工作流。

用户输入主要包括一句自然语言需求、当前账号、要处理的家庭成员，以及是否已经确认关键动作。比如用户说“我爸的降压药只剩三天了，帮我准备续方”。工作流先提取家庭成员、任务类型和还缺哪些信息，再校验这个成员是否属于当前账号。接着按任务类型分支：续方会查询健康档案、历史处方和药箱；复诊材料整理会查询健康档案、历史处方和已有资料；创建提醒会查询药箱和原处方；涉及停药、加量、减量、换药或严重症状时，直接进入 Agent 安全分支。

查询结果不会直接让模型自由发挥，而是先汇总成结构化资料，再检索续方规则、提醒规则或医疗安全规则。模型只负责根据这些资料整理回答或生成待确认草稿。最后还有一个条件判断：如果缺少信息，就输出需要用户补充的内容；如果命中高风险，就输出风险提示并建议联系医生；如果属于复诊、购药或提醒创建，就先返回预览并等待用户确认，不能直接执行。

最终输出不只是一段文字，还包括处理的是谁、识别到的任务、当前状态、缺失信息、资料来源、风险标记、是否需要确认，以及确认后的草稿编号。这样前端既能展示自然语言答案，也能根据状态展示“补充信息”或“确认”按钮。

需要说明的是，当前医院项目仓库里的正式编排使用 LangGraph。这里的 Dify 回答，是结合我实习中使用 Dify 的经验，把同一套业务流程映射成可视化工作流的设计，不会说成已经用 Dify 在医院项目里上线。

### Q67：Dify 工作流的节点按顺序怎么连接？

**参考回答（口头版）：**

我会把主链路讲成下面几步：

1. `开始`节点接收用户问题、账号、家庭成员和确认状态。
2. `参数提取器`识别家庭成员、任务类型、药品、剩余天数和缺失信息。
3. `HTTP 请求`节点调用后端校验当前账号是否有权访问该家庭成员，`代码执行`节点补充字段格式和基础风险词检查。
4. `条件分支`按续方、复诊材料、用药提醒和高风险问题分流。
5. 各业务分支通过 `HTTP 请求`调用后端接口，读取档案、处方、药箱或药店库存；医疗规则通过`知识检索`节点查询。
6. `变量聚合器`把业务数据和知识库资料汇合，同时保留资料来源。
7. `大模型`节点只生成资料整理结果或待确认草稿，不直接修改处方，也不执行购药和提醒创建。
8. Agent 安全检查通过规则、`代码执行`和`条件分支`实现，再次判断是否涉及改药、严重症状、成员越权或跳过确认。
9. 最后一个`条件分支`根据结果进入“补充信息”“风险拦截”“等待确认”或“完成”四种出口。
10. `结束`节点输出统一结构，前端根据状态继续交互。

如果面试官问连线，可以直接说：`开始`连`参数提取器`，然后通过 `HTTP 请求`校验成员权限，再进`条件分支`；各业务分支分别查数据，之后在`变量聚合器`汇合，再经过`大模型`整理和 Agent 安全检查，最后按补充、拦截、待确认、完成四种状态进入`结束`。

### Q68：Dify 工作流具体输入什么，输出什么？

**参考回答（口头版）：**

输入分两类。用户输入是自然语言问题，例如“我爸的降压药只剩三天了”；系统输入是当前账号、家庭成员编号、任务编号和是否已经确认。第二轮确认时还会带上上一轮的任务编号，避免把一句“确认”重新理解成新任务。

中间节点统一传递结构化字段，包括家庭成员、任务类型、缺失信息、处方和药箱查询结果、知识库资料来源、风险标记以及是否需要用户确认。模型只能读取这些字段，不能绕过后端直接查数据库。

输出会包含给用户看的回答，也会包含给前端和后端使用的状态字段，例如 `status`、`need_confirmation`、`missing_fields`、`source_refs`、`risk_flags` 和 `draft_id`。面试时不需要逐个背字段，可以概括为“回答内容、流程状态、资料来源、风险结果和待确认草稿”。

### Q69：为什么不让 Dify 里的模型直接决定调用什么、最后直接执行？

**参考回答：**

因为这个项目处理的是家庭成员、处方和用药信息，错误成本比较高。模型可以帮助理解自然语言和整理资料，但成员权限、任务路由、高风险判断和用户确认必须由明确规则控制。否则模型一旦识别错成员、漏掉确认或错误调用写操作，后果无法只靠提示词兜底。

所以我会把 Dify 用在流程可视化、参数传递、知识检索和模型节点编排上，把真实数据查询、权限校验、幂等和草稿保存放在后端。Dify 负责“怎么走流程”，后端负责“哪些数据能读、哪些动作能做”。

### Q70：Dify 工作流怎样处理用户确认和多轮对话？

**参考回答（口头版）：**

第一轮自动生成无外部副作用的本地草稿，同时冻结任务编号、摘要、资料来源和运行轨迹。前端展示草稿和确认执行按钮；用户确认后发起第二次独立 run，并携带原任务编号、草稿版本和幂等键。后端从 PostgreSQL checkpoint 恢复进度，重新校验账号、家庭成员和可变资料，再执行当前系统允许的本地状态迁移；它仍不会真实提交医院、药店或通知系统。

如果用 Dify 的 `Chatflow`，可以用会话变量临时保存任务编号和当前步骤；如果用普通 `Workflow`，第二次调用就由前端明确传回任务编号。无论哪种方式，复诊、购药和提醒创建的确认状态都以后端记录为准，不能只存在 Dify 会话里。

我不会仅凭用户回复“好的”就让模型猜是在确认哪一个动作，也不会把整段历史对话重新塞给所有节点。这样既能支持多轮补充，也能避免页面刷新、重复点击或上下文过长导致重复创建。

## 7. 容易失分的回答修正

不要直接说：

- “代码能力不重要，因为以后 100% 都是 AI 生成。”
- “Cursor 和 Claude Code 没什么区别，只是 Cursor 便宜。”
- “我了解 OpenClaw 的具体内部实现”，但实际上只看过概念。
- “RAG 就是向量检索，rerank 不清楚。”
- “Harness 指标证明了临床安全。”

更好的表达是：AI 改变代码生产方式，但工程师仍要负责需求、契约、验证、部署、维护和风险；RAG 要区分召回、排序、来源、权限和安全；评测结果必须说明数据集、环境和测量范围。
