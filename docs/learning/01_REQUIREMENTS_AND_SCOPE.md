# 01. 从需求到可交付范围

## 1. 从一句想法开始

原始想法通常像“做一个家庭健康 Agent”。这不足以直接写代码，因为它没有说明谁使用、输入是什么、成功长什么样、哪些错误绝不能发生。

本项目把它缩成四个可演示场景：续方材料、复诊材料、提醒草稿和高风险拦截。每个场景都要求同一组可验证条件：有成员身份、有证据来源、有安全边界、有确认步骤、有 trace。

这是一种重要的需求拆解技巧：**先找共同的质量约束，再写各场景业务差异。**

## 2. 功能需求与约束需求

| 类型 | 示例 | 代码会受到什么影响 |
| --- | --- | --- |
| 功能需求 | 查询父亲的处方、药箱和库存。 | 需要 models、service、工具和后续 API。 |
| 安全约束 | 不能建议用户加量或停药。 | 需要 SafetyAgent、禁用表达测试和确认门禁。 |
| 隔离约束 | 不能把母亲的记录给父亲任务。 | 每个查询、Context 与来源引用都带 `member_id`。 |
| 审计约束 | 要知道工具做过什么。 | ToolResult、ToolCallTrace、AgentToolCall 记录输入输出与失败。 |
| 产品边界 | 不向医院真实提交。 | 草稿工具固定标记 `not_submitted`。 |

很多初学者只写第一行，随后在测试或面试中被“安全吗”“怎么防串数据”追问卡住。真正的工程需求要把后四行一起写出来。

## 3. 为什么先定义非目标

医疗场景最危险的需求不是“少做了什么”，而是系统看起来好像做了不该做的事。因此 PRD 先写：不诊断、不自动开方、不改剂量、不绕过人工确认、不编造来源。

非目标会改变架构。例如：

- 因为不自动开方，`Prescription` 是已有医生处方的快照，Agent 只读取和整理它。
- 因为不真实下单，`PurchasePlan` 是 draft，不是订单表。
- 因为不能凭记忆说病史，Context 中传播的是 `ToolEvidenceRef` 而不是一段自由文本结论。

## 4. 用户故事如何变成验收条件

以“帮我整理父亲的续方材料”为例：

```text
Given: 已选择父亲 member_id，且有处方、药箱、购药记录
When: 系统运行续方流程
Then: 只调用当前角色允许的工具
  And: 每项事实都能指向 evidence source
  And: 输出是材料或草稿，不是处方和剂量建议
  And: 如需创建草稿，必须先等待用户确认
```

这类 Given/When/Then 会自然变成 fixture 和测试名称。需求不是 PPT；一个好需求应该能直接导向测试。

## 5. 为什么需要阶段路线图

不能同时做数据库、API、LLM、LangGraph 和前端。它们依赖关系很强：API 要读 service，service 要有模型，Agent 要有工具，工具要有契约，真实编排要有可回放 trace。

所以路线图先完成数据库与 trace，再完成 Context/Tool/Harness 的确定性基线，之后才做读取 API、写 API、RAG、模型、图工作流和 UI。每一阶段都规定“要做什么、怎么验收、不做什么”。这就是控制项目膨胀的方式。

## 6. 练习

选择“查询药店库存”这一需求，自己写出：

1. 一个用户故事。
2. 三条功能验收条件。
3. 三条安全或隔离验收条件。
4. 它应该涉及哪些层，哪些层不该改。

完成后对照 [PRD.md](../PRD.md)、[API_SPEC.md](../API_SPEC.md) 和 [AGENT_WORKFLOW.md](../AGENT_WORKFLOW.md)。
