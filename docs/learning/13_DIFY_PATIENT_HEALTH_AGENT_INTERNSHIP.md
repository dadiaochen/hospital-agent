# 13. Dify 患者端医疗智能体实习项目

> 本文依据《Dify 患者端医疗智能体完整搭建教程》整理，用于简历复盘和面试准备。
>
> 当前能够确认的实现是：在现有 Dify Chatflow 上搭建可演示、可测试的患者端医疗智能体原型。五个业务分支读取的是模拟业务数据，尚不能表述为已经接入公司的真实患者档案、处方、药房库存、舌诊或报告系统。

## 1. 项目背景与定位

实习公司的原有业务模式与互联网医院相似：

1. 患者端发起在线问诊；
2. 医生端接诊并开具处方；
3. 患者回到患者端查看处方并购药；
4. 公司还提供智能舌诊能力。

这些基础业务在进入实习前已经存在。我的工作不是重新开发问诊、开方或购药系统，而是使用 Dify 增加一个面向患者的医疗智能体入口，把患者在不同业务阶段需要准备的信息、已有结果解释和下一步操作串联起来。

项目覆盖五个真实业务分支：

1. 问诊前准备；
2. 慢病复诊；
3. 诊后用药与购药；
4. 智能舌诊；
5. 报告解读。

智能体只做信息整理、已有结果解释和流程引导，不做疾病诊断，不开具或修改处方，不建议患者自行加量、减量、停药或换药，也不自动下单和支付。

## 2. 为什么使用 Chatflow

患者会使用自然语言连续补充症状、处方、报告编号或页面来源，因此入口采用 Dify Chatflow，而不是一次输入后直接结束的 Workflow。

选择一张 Chatflow 的原因：

- 五个场景共享意图识别、风险判断、知识检索和最终答复；
- 患者场景不明确时需要继续追问；
- 原型阶段可以复用公共节点，减少重复配置；
- 后续接入真实系统时，可以逐个替换五个数据节点，不需要重做主流程。

这不是“让模型自由决定所有步骤”。场景路由由明确的条件分支控制，高风险内容由统一规则约束，模型主要负责理解自然语言和生成患者能看懂的说明。

## 3. 完整画布与节点连线

```text
用户输入
  ↓
意图识别与信息提取
  ↓
业务场景分流
  ├─ 问诊前准备数据
  ├─ 慢病复诊数据
  ├─ 诊后用药与购药数据
  ├─ 智能舌诊数据
  ├─ 报告解读数据
  └─ 场景确认回复
        ↓
业务数据汇总
  ↓
医疗流程知识检索
  ↓
患者答复与安全检查
  ↓
直接回复
```

这张画布是在原有流程上增量修改的：

```text
用户输入
→ INTENT_RECOGNITION
→ MOCK_BUSINESS_CONTEXT
→ RETRIEVE_SOP_CONTEXT
→ FINAL_PLAN_GENERATOR
→ 直接回复
```

具体改造方式：

1. 将原有英文节点改成便于业务沟通的中文名称；
2. 复制原有业务数据节点，形成五个业务分支；
3. 在意图识别后增加条件分支；
4. 在五个分支后增加变量聚合器；
5. 保留统一的知识检索、答复生成和直接回复节点。

## 4. 输入与输出

### 4.1 Chatflow 输入

| 输入变量 | 作用 |
|---|---|
| `query` | 患者本轮自然语言问题 |
| `page_source` | 患者当前所在页面，如首页、问诊页面、处方页面、购药页面、舌诊页面、报告页面 |
| `resource_id` | 当前处方、报告、舌诊结果等资源标识 |
| `login_status` | 判断是否具备读取患者相关业务数据的前置条件 |

`query` 是主要输入，其他变量用于减少歧义。例如患者只说“帮我看看这个”，系统可以结合报告页面和 `resource_id` 路由到报告解读，而不是让模型猜测“这个”指什么。

### 4.2 意图识别输出

“意图识别与信息提取”节点输出：

| 字段 | 含义 |
|---|---|
| `intent` | 五个业务场景之一，或场景不明确 |
| `confidence` | 当前意图判断的置信程度 |
| `provided_info` | 患者已经提供的信息 |
| `missing_info` | 继续处理前仍需补充的信息 |
| `risk_level` | 当前问题的风险等级 |
| `risk_reason` | 判定为高风险的原因 |

教程示例中使用低随机性的模型配置，目的不是让回答更有创意，而是提高路由和字段输出的稳定性。

### 4.3 最终输出

患者可见答复统一使用四段结构：

1. 当前场景；
2. 已确认信息；
3. 需要补充或注意；
4. 下一步操作。

“直接回复”节点只引用“患者答复与安全检查”节点的最终文本，不直接暴露 JSON、内部变量、知识库片段或模拟接口原始数据。

## 5. 五个业务分支

### 5.1 问诊前准备

**输入：** 患者问题、页面来源、登录状态。

**处理：**

- Code 节点返回模拟患者档案和本次问诊准备信息；
- 整理主诉、症状持续时间、既往病史、过敏史、当前用药和已有检查资料；
- 缺少关键材料时，明确告诉患者还需要补充什么。

**输出：** 一份问诊材料清单和下一步操作，不判断患者患有什么疾病。

### 5.2 慢病复诊

**输入：** 患者问题、模拟历史处方和剩余药量。

**处理：**

- 读取模拟历史处方；
- 展示处方来源、药品信息和预计剩余天数；
- 整理复诊需要准备的近期指标、用药反馈和异常情况；
- 将“预计剩余三天”等信息作为复诊提醒依据。

**输出：** 复诊材料和流程提示，不自动续方，不修改医生处方。

### 5.3 诊后用药与购药

该分支同时覆盖处方解释、购药流程和用药咨询。

**输入：** 患者问题、模拟处方、药房库存和配送信息。

**处理：**

- 解释医生已经开具的药品名称、处方用法和注意事项；
- 根据模拟库存展示可选药房和配送信息；
- 当患者询问两种药能否一起使用时，读取字段 `drug_interaction_status`；
- 教程数据明确标记“未接入真实药物相互作用服务”，因此不能根据模型常识给出确定结论。

**输出：** 已有处方解释、购药候选信息和咨询医生或药师的提示。系统不替患者下单，不推荐替代药，不调整剂量。

### 5.4 智能舌诊

**输入：** 患者问题和舌诊结果标识。

**处理：**

- 测试标识 `TONGUE_TEST_3001` 返回模拟的已完成舌诊报告；
- 其他标识进入等待上传或等待结果状态；
- 智能体只解释已有舌诊结果和下一步就医建议。

**输出：** 对已有舌诊结果的通俗说明，不生成新的中医诊断。

### 5.5 报告解读

这是正式的第五个业务分支，不是后续优化设想。

**输入：** 患者问题和报告标识。

**处理：**

- 测试标识 `REPORT_TEST_2001` 返回模拟血常规报告；
- 其他标识进入等待上传或等待报告状态；
- 解释报告项目、参考范围和已有异常标记；
- 将单项异常与确诊疾病严格区分。

**输出：** 报告指标说明、需要关注的信息和复诊建议，不根据单个指标作疾病诊断。

## 6. 业务数据汇总

五个 Code 节点统一输出字符串变量 `branch_payload`。变量聚合器收集各分支的 `branch_payload`，将实际命中的一条业务结果交给后续节点。

统一数据结构有两个作用：

1. 下游知识检索和最终答复不需要理解五套不同变量；
2. 后续将 Code 节点替换成 HTTP 请求节点时，只要保持输出契约不变，后续画布不需要重连。

当前版本使用 Code 节点模拟公司业务接口返回。这是为了完整验证画布，不代表已经读取真实患者数据。

## 7. 医疗流程知识库

知识库名称：

```text
互联网医院患者服务与安全知识库
```

知识库覆盖：

- 问诊准备资料；
- 慢病复诊流程；
- 处方解释与购药流程；
- 智能舌诊使用说明；
- 报告解读边界；
- 高风险问题的转人工规则。

教程中的分段设置：

| 配置 | 取值 |
|---|---|
| 分段模式 | 通用 |
| 分段标识符 | 空行 |
| 最大分段长度 | 800 |
| 分段重叠长度 | 100 |
| 索引方式 | 高质量 |
| Embedding 模型 | Dify 中已配置且可正常使用的中文 Embedding 模型 |

检索使用混合检索，教程建议 `Top K = 4`，支持阈值时可设置约 `0.3`。这些参数是原型配置，不表述为经过线上数据证明的最优参数。

检索查询应结合患者问题、识别出的场景和缺失信息，而不是只使用原始问题。业务事实来自数据节点，知识库提供流程规则和安全边界，两者不能混用。

## 8. 患者答复与安全检查

最终节点同时接收：

- 患者原始问题；
- 意图、已提供信息和缺失信息；
- 聚合后的业务数据；
- 知识库召回内容；
- 风险等级和风险原因。

生成答复时遵守以下边界：

1. 不诊断疾病；
2. 不生成或修改处方；
3. 不建议自行调整药物；
4. 不根据模型常识判断药物能否同服；
5. 不自动下单、支付或执行真实业务操作；
6. 高风险症状、停药、加量、换药等请求引导患者联系医生、药师或及时就医；
7. 报告和舌诊只解释已有结果，不把解释写成诊断结论。

这里在面试中称为“Agent 安全”或“医疗安全边界”，不写成“安全代理”“safeagent”或“safe 代理”。

## 9. 测试与排查

### 9.1 测试范围

教程至少覆盖以下用例：

1. 问诊前准备；
2. 慢病复诊；
3. 处方解释；
4. 药物相互作用咨询；
5. 购药咨询；
6. 智能舌诊；
7. 报告解读；
8. 页面来源与资源标识不一致；
9. 高风险用药问题；
10. 场景不明确。

当前文档不写通过率、准确率或线上效果指标。

### 9.2 排查顺序

当结果异常时，按节点顺序检查：

1. 意图是否识别正确；
2. 风险是否被识别；
3. 条件分支是否进入正确场景；
4. Code 节点是否输出 `branch_payload`；
5. 变量聚合器是否收到分支输出；
6. 知识库是否召回对应流程；
7. 最终节点是否同时收到业务数据和知识片段；
8. 直接回复是否只输出最终文本。

### 9.3 常见错误

- Code 节点输入变量名与代码引用不一致；
- Code 节点返回的不是字符串；
- 变量聚合器没有包含所有分支；
- 最终答复泄露 JSON 或内部变量；
- 知识检索没有命中对应流程；
- 报告解读被模型写成疾病诊断；
- 模型绕过真实药物相互作用服务，直接给出确定结论。

## 11. 口头介绍

### 11.1 60 至 90 秒版本

> 我实习的公司主要做互联网医院业务，患者可以在线发起问诊，医生接诊和开方后，患者再回到患者端购药，公司也已经有智能舌诊服务。我入职时这些业务已经能够独立运行，我的工作是用 Dify 增加一个面向患者的医疗智能体入口，帮助患者理解自己现在处于哪个环节、还缺什么信息以及下一步该做什么。
>
> 我把需求整理成了五个场景：问诊前准备、慢病复诊、诊后用药和购药、智能舌诊、报告解读。入口先识别患者的意图、已经提供的信息、缺失信息和风险等级，再通过条件分支进入对应场景。每个场景用 Code 节点模拟一次业务接口返回，随后统一汇总数据、检索医疗流程知识，最后生成患者能看懂的说明和下一步操作。
>
> 这项工作最难的是控制医疗边界。模型只能解释业务数据和知识库中已有的内容，不能诊断、开方、修改剂量或直接购药。患者问两种药能不能一起用时，因为原型没有接入可靠的药物相互作用服务，所以不会根据模型常识下结论，而是提示咨询医生或药师。当前完成的是可演示、可测试的原型，后续接真实系统时可以逐个替换数据节点，不需要重新设计主流程。

这段话按背景、任务、行动和结果检查完整性，但口头表达不念 STAR 字母，也不在开头堆技术栈。

### 11.2 30 秒版本

> 我在互联网医院实习中用 Dify 做了一个患者端医疗智能体原型，把问诊前准备、慢病复诊、诊后用药与购药、智能舌诊和报告解读放到一个对话入口里。系统先识别意图和风险，再进入对应分支，汇总模拟业务数据并检索医疗流程知识。它只帮助患者整理信息、理解已有结果和确认下一步，不替代医生诊断、开方或调整用药。

## 12. 面试问题与参考回答

### Q1：这个 Dify 项目主要解决什么问题？

**参考回答：**

原有在线问诊、开方、购药和舌诊业务已经存在，但患者需要自己判断应该进入哪个页面、准备什么资料以及下一步做什么。我做的患者端医疗智能体把五个常见场景放进一个对话入口，通过意图识别和条件分流连接已有业务，再结合医疗流程知识生成下一步指引。

### Q2：为什么选择 Dify？

**参考回答：**

这项任务首先要验证业务流程，而不是重新开发一套 Agent 平台。Dify 已经提供对话入口、条件分支、Code 节点、知识检索、模型调用和调试能力，能够快速搭出完整链路。我的重点放在场景拆分、变量设计、业务数据契约和医疗安全边界上。

### Q3：是 Chatflow 还是 Workflow？

**参考回答：**

实际搭建的是 Chatflow。患者经常需要补充症状、处方、报告编号或页面上下文，场景不清楚时也要继续追问，所以需要保留对话过程。五个场景没有拆成五个独立应用，而是在一张 Chatflow 中通过条件分支路由，共用后面的数据汇总、知识检索和安全答复节点。

### Q4：你自己搭的 Workflow 具体怎么连？

**参考回答：**

患者输入先进入“意图识别与信息提取”，输出场景、已提供信息、缺失信息和风险等级；然后进入“业务场景分流”，分别连接问诊前准备、慢病复诊、诊后用药与购药、智能舌诊和报告解读五个 Code 节点。五个节点统一输出 `branch_payload`，由变量聚合器汇总，再进入医疗流程知识检索，最后由患者答复与安全检查节点生成回复，直接回复节点只展示这段最终文本。

### Q5：输入和输出分别是什么？

**参考回答：**

输入包括患者问题、当前页面来源、资源标识和登录状态。中间结构化输出包括意图、已提供信息、缺失信息、风险等级和风险原因。五个业务分支输出统一的业务数据字符串。最终输出固定为当前场景、已确认信息、需要补充或注意、下一步操作四部分。

### Q6：为什么放在一张画布里？

**参考回答：**

五个场景共享入口、意图识别、风险判断、知识检索和最终答复。原型阶段放在一张画布里能复用这些公共节点，也方便端到端调试。场景数量和团队协作规模继续扩大后，可以把具体业务分支拆成独立 Workflow，由入口 Chatflow 调用。

### Q7：Code 节点里做了什么？

**参考回答：**

Code 节点用于模拟患者档案、历史处方、药房库存、舌诊结果和检查报告等业务接口返回，并把各分支结果转换成统一的 `branch_payload`。它的价值是先固定数据契约，后续替换成 HTTP 请求节点时，下游聚合、检索和答复节点不用重做。

### Q8：项目有没有接真实后端接口？

**参考回答：**

教程对应的版本没有接真实业务接口，五个分支读取的是模拟数据。它验证的是完整业务链路和接口输出结构，不能说成已经读取真实患者档案、处方或库存。真实接入时还需要完成身份校验、患者授权、接口鉴权、超时重试、审计和敏感信息保护。

### Q9：知识库怎么搭建？

**参考回答：**

我建立了“互联网医院患者服务与安全知识库”，内容覆盖五个患者场景的流程说明和医疗边界。教程采用通用分段，空行切分，最大长度 800、重叠 100，高质量索引和中文 Embedding 模型。检索使用混合检索，召回少量最相关片段供最终节点使用。

### Q10：为什么业务数据和知识库要分开？

**参考回答：**

患者处方、库存、报告和舌诊结果属于当前业务事实，应来自业务接口；复诊流程、报告解释边界和高风险处理规则属于知识，应来自知识库。把两者分开可以避免模型把通用知识误写成患者事实，也便于分别更新和审计。

### Q11：检索参数怎么设置？

**参考回答：**

教程原型使用混合检索，`Top K` 取 4，支持阈值时设置约 0.3。这个配置是为了控制进入提示词的片段数量，不能说成线上最优值。真正调优需要基于标注问题集比较召回率、排序质量、最终回答正确性、延迟和 Token 消耗。

### Q12：为什么用混合检索？

**参考回答：**

医疗流程中既有“慢病复诊”“处方有效期”这样的明确关键词，也有“药快吃完了怎么办”这样的口语表达。关键词检索适合精确术语，向量检索适合语义相近表达，混合检索可以兼顾两类问题。

### Q13：报告解读怎么做？

**参考回答：**

报告解读是第五个正式分支。原型根据报告标识读取模拟报告，解释检查项目、参考范围和已有异常标记，再结合知识库说明复诊时需要关注什么。系统不会根据单项指标判断疾病，也不会把模型生成内容写成诊断结论。

### Q14：智能舌诊怎么做？

**参考回答：**

智能舌诊分支读取已有舌诊结果并做通俗解释。原型用测试标识区分“已有结果”和“等待上传或处理”两种状态。患者智能体不重新分析舌象，也不生成新的中医诊断。

### Q15：患者问两种药能不能一起吃，怎么回答？

**参考回答：**

原型没有接入可靠的药物相互作用服务，数据中也明确标记为未接入，所以不能靠模型常识给出“可以”或“不可以”的确定结论。系统会展示已有处方信息，说明存在需要核实的用药风险，并引导患者咨询开方医生或药师。

### Q16：购药分支会直接下单吗？

**参考回答：**

不会。它只根据模拟库存展示药房、配送等候选信息，并解释下一步操作。真实下单和支付必须回到业务系统，由患者确认后执行，模型不能替患者完成关键动作。

### Q17：如何识别高风险问题？

**参考回答：**

意图识别节点同时输出风险等级和风险原因，最终节点再执行统一的医疗边界检查。涉及严重症状、自行停药、加量、减量、换药或跳过医生确认时，不继续给普通流程建议，而是提示及时联系医生、药师或就医。

### Q18：场景识别错了怎么办？

**参考回答：**

先用页面来源和资源标识辅助判断，减少只看自然语言造成的歧义。意图置信不足或缺少关键信息时，路由到“场景确认回复”，让患者补充或选择场景，不强行进入某个业务分支。

### Q19：为什么不能让大模型自己选工具和路径？

**参考回答：**

这是医疗流程，路由错误会把错误的业务数据和规则带入回答。原型让模型负责理解自然语言，但实际分支由条件节点控制，业务数据由固定节点读取，最终答复受统一边界约束。这样比完全自由的循环更容易测试和复盘。

### Q20：如何测试这张画布？

**参考回答：**

我按五个正常场景、药物相互作用、购药、跨资源、高风险和意图不明确等类型设计测试。出现问题时从意图、风险、路由、Code 输出、变量聚合、知识召回、最终节点输入和直接回复逐层检查，而不是只看最后一句回答。

### Q21：常见的错误案例有哪些？

**参考回答：**

主要有路由到错误场景、Code 节点没有返回字符串、变量聚合器漏接分支、知识库没有命中、最终回复泄露 JSON、把报告解读写成诊断，以及模型绕过药物相互作用服务直接下结论。每类错误都能定位到具体节点。

### Q22：这个项目的最大难点是什么？

**参考回答：**

最大难点不是把节点连起来，而是让回答既有帮助又不越过医疗边界。业务事实、流程知识和模型解释必须分开；没有接口或知识来源时不能补全；诊断、处方调整、药物相互作用和真实下单都必须明确限制。

### Q23：如果接入真实业务系统，怎么改？

**参考回答：**

保留入口、路由、聚合、检索和答复节点，把五个 Code 节点逐步替换成 HTTP 请求节点，并保持统一输出结构。同时补充身份校验、患者授权、成员隔离、接口鉴权、超时重试、幂等、审计和用户确认。处方、库存和报告只相信接口返回，不相信模型记忆。

### Q24：Dify 方案有什么不足？

**参考回答：**

原型适合快速验证，但随着场景和团队规模增加，一张画布会变复杂；版本管理、自动化测试、细粒度权限和运行审计也弱于代码化系统。后续可以拆分业务 Workflow，稳定规则和核心执行链路逐步迁移到后端，Dify 保留运营配置和快速验证能力。

### Q25：Dify 项目和个人互联网医院项目是什么关系？

**参考回答：**

Dify 项目是实习中的患者端业务原型，重点是五个场景的流程编排、知识检索和医疗边界。个人互联网医院项目是在相似业务背景下继续做工程化练习，重点是家庭成员隔离、统一工具调用、运行记录、人工确认和 Agent 评测。两者共享业务理解，但不混用公司代码、数据和交付结论。

### Q26：Dify 的 Function Calling 和 MCP 有什么区别？

**参考回答：**

Function Calling 是模型按结构化参数选择函数的调用机制；MCP 是工具、资源和提示词如何被客户端发现与调用的标准协议；Dify Workflow 是业务流程编排。三者不在同一层。这个原型主要使用 Dify 节点和条件分支，没有把 MCP 说成已实现能力。

### Q27：为什么不直接做成多 Agent？

**参考回答：**

五个分支的职责清楚，流程也有明确边界，使用条件路由更直接、更容易测试。为了展示多 Agent 而拆出多个角色会增加上下文传递和错误定位成本。只有任务需要不同权限、独立状态或并行执行时，才值得拆成多个 Agent。
