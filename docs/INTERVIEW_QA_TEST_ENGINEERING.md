# 备选：测试开发面试经验

这份文档面向测试开发、质量工程和测试平台岗位，重点记录本项目与实习经历中的测试设计、质量保障和问题定位。后端开发与大模型应用岗位的项目和 Agent 追问见 [后端与大模型应用开发面经](INTERVIEW_QA.md)。通用 Java、MySQL 和算法八股不再混入本项目文档。

> **面试术语规则：** 本文使用测试开发面试中的自然表达，统一写“Agent 安全”“Agent 评测”等面试说法；代码类名、内部模块名只在确有必要说明实现契约时使用，不直接替代面试术语。

## 1. pytest 与算法测试

### Q1：如何用 pytest 测试一个算法？

**参考回答：**

先拆成确定性单元、边界、异常、参数化和必要的集成测试。`fixture` 管理共享输入和资源，`parametrize` 覆盖多组边界，`mock` 隔离外部服务，但不会把所有依赖都 mock 掉。

```python
import pytest

@pytest.mark.parametrize(
    ("remaining", "daily", "expected"),
    [(6, 2, 3), (0, 2, 0)],
)
def test_remaining_days(remaining, daily, expected):
    assert estimate_days(remaining, daily) == expected
```

如果输入是图片，会使用固定 fixture 目录，记录尺寸、格式、标签和必要的脱敏信息。测试不依赖微信临时路径，也不把个人数据写入仓库。

### Q2：pytest 中用过哪些具体特性？

**参考回答：**

常用 `fixture` 管理数据库、临时目录和测试客户端，`parametrize` 覆盖输入组合，`monkeypatch` 修改配置，`mock` 隔离外部 API，`pytest-cov` 观察覆盖率，`pytest-xdist` 在测试可并行时提升速度。对于 Agent 测试，还会用固定的本地模型响应，避免把真实模型作为 CI 的前置条件。

### Q3：非确定性算法如何评估？

**参考回答：**

不能只写精确等值断言。先定义召回率、准确率、Top-K 命中、输出格式通过率、回答来源支撑、安全召回和延迟分位数，再使用固定随机种子、固定测试数据、重复运行和统计阈值判断。医疗安全拦截属于硬约束，不能用平均分掩盖一次危险漏拦截。

### Q4：如何关注算法性能？

**参考回答：**

测 p50/p95 延迟、吞吐、CPU、内存和输入规模增长趋势；Python 先 profile 再优化。Agent 场景要拆分模型、RAG、数据库和工具耗时，避免只看总耗时。优化可以考虑缓存、批处理、索引、减少无效上下文和并行 IO，同时保留结果一致性和审计能力。

## 2. 测试开发与质量工程

### Q5：大模型生成的测试用例可信吗？

**参考回答：**

可以把大模型当测试设计助手，不能当可信 oracle。它可以生成边界候选、异常矩阵和参数化数据，但必须由工程师检查断言、敏感数据、业务规则和可执行性。生成的测试还要经过 lint、pytest、review 和覆盖率检查，数量多不等于质量高。

### Q6：测试报告应该包含哪些信息？

**参考回答：**

至少包括版本和环境、执行命令、用例总数、通过、失败、跳过、失败详情、覆盖率、耗时、性能指标、风险分级和结论。Agent 还应增加工具调用准确性、来源引用、输出格式、人工确认、安全召回、上下文隔离和降级处理统计。

### Q7：CI 上的自动化用例经常不稳定，怎么排查？

**参考回答：**

先区分产品缺陷、测试缺陷和环境问题，再保留失败日志、随机种子、输入、服务版本和 Trace。重点排查真实时间、网络、共享状态、并发竞争、异步任务、端口和外部依赖。修复根因后可以有限重试，但不能用无限重试掩盖 flaky 测试。

### Q8：遇到无法复现的 Bug 怎么处理？

**参考回答：**

收集最小复现信息：输入、家庭成员和任务范围、版本、环境、时间线、日志、运行轨迹和依赖版本。然后缩小为可重复的测试数据或回放用例，修复后补回归测试。Agent 问题尤其要保留完整运行轨迹、工具输入输出和安全标记，不能只看最终文本。

### Q9：新需求上线前如何安排测试？

**参考回答：**

先读需求和风险，明确正常路径、边界、异常、权限和回滚，再按单元、集成、API/UI、E2E 和回归分层。医疗 Agent 还要覆盖跨成员隔离、无来源、工具失败、缺确认、高风险拦截和重复确认幂等。上线前检查监控、日志、feature flag、数据库迁移和回滚方案。

### Q10：你还用过哪些测试框架或工具？

**参考回答：**

Python 后端常用 pytest、pytest-cov、httpx/TestClient、mock、ruff 或 mypy；接口调试可以用 Swagger、curl 或 Postman；CI 使用 GitHub Actions 等自动化执行。工具本身不是重点，重点是测试分层、失败可诊断、结果可复现。

### Q11：你对测试开发岗位的长期规划是什么？

**参考回答：**

短期把业务、接口、数据和自动化基础做扎实，能独立设计稳定用例和定位问题；中期深入质量工程，包括测试平台、CI、性能、可观测性和测试数据治理；长期希望把 AI Agent 用在测试设计、失败归因和回归分析上，同时保留人工定义质量标准和风险边界的责任。

## 4. AI 代码测试与 Agent 质量

### Q12：大模型生成的单测代码可以直接合并吗？

**参考回答：**

不能。大模型适合生成测试候选、边界组合和 mock 草稿，但不是真实 oracle。工程师要检查需求覆盖、断言是否有效、是否误测实现细节、是否引入敏感数据，以及测试在真实依赖变化时是否仍然有意义。

生成代码必须经过格式检查、静态检查、测试运行、review 和必要的变异测试；“能跑通”不等于“测到了问题”。

### Q13：哪些代码不适合直接生成单元测试？如何识别？

**参考回答：**

强依赖数据库、RPC、时间、随机数、线程、文件系统或外部模型的代码，不适合不加隔离地直接生成单测；高耦合、隐藏全局状态和大量动态反射的代码也容易生成表面覆盖。

先按调用关系和副作用识别边界，把纯函数与外部依赖拆开；对外部依赖使用契约明确的 mock 或 fake，对关键链路补集成测试，而不是把所有东西都 mock 掉。

### Q14：覆盖率很高但测试质量很差，怎么解决？

**参考回答：**

覆盖率只说明代码路径被执行过，不能证明断言有效。要结合分支/条件覆盖、关键业务路径、异常路径、变异测试、缺陷逃逸率、测试稳定性和人工 review 判断质量。

如果覆盖率高但线上仍出问题，应检查是否缺少有意义的断言、边界数据、错误处理和跨模块契约，而不是继续堆测试数量。

### Q15：mock 什么时候是必要的？什么时候会降低质量？

**参考回答：**

不可控、昂贵或有副作用的外部依赖，例如真实 RPC、支付、模型服务和时间源，通常需要 mock 或 fake 来保证单测稳定。业务核心逻辑、序列化契约和数据库查询不能全部 mock，否则测试只证明 mock 的返回值。

对稳定接口可以增加少量集成测试或 contract test，验证 mock 与真实服务之间没有明显偏差。

### Q16：AST、调用关系和 LSP 在 AI 生成单测中有什么作用？

**参考回答：**

AST 可以解析函数、类、分支、异常和装饰器等结构，调用关系可以帮助识别依赖边界，LSP 可以提供符号、类型、定义和引用信息。它们能为模型提供比整段源码更结构化的上下文，并筛选适合生成测试的函数。

但动态语言中的反射、运行时装配和隐式副作用不能只靠 AST/LSP 判断，最终仍需要执行测试、检查失败路径和人工确认。

### Q17：如何评估 AI 生成测试用例的效果？

**参考回答：**

除了通过率和覆盖率，还要看断言有效性、变异分数、缺陷检测率、关键路径覆盖、重复率、flaky 率、执行耗时和人工采纳率。对于 Agent 测试，还要增加工具调用准确性、来源支撑、输出格式、安全召回和上下文隔离。

评估集要固定版本和输入，区分测试生成质量与被测系统质量，不能把模型生成的测试直接当作正确答案。

### Q18：文本和图片输入、生成视频的模型，如何测试安全性？

**参考回答：**

建立覆盖正常内容、敏感内容、越权指令、间接 Prompt Injection、隐私泄露、版权风险和高风险动作的测试集，分别检查输入识别、策略拦截、输出内容和工具调用。对于拒答类用例，要定义允许的安全解释和禁止的泄露信息。

测试结果应记录模型版本、提示词、图片来源、随机种子、策略版本和输出审核结果；安全拦截属于硬约束，不能用平均通过率掩盖单个高风险漏拦截。

### Q19：Agent Harness 如何和测试开发流程结合？

**参考回答：**

把固定用例、测试数据、工具调用记录、RAG 来源、最终回答和评测结果纳入回归资产。CI 先使用固定的本地模型响应，验证路由、权限、输出格式、用户确认、失败降级和成员隔离，再把真实模型评测作为独立任务。

失败时保留输入、状态、工具调用、耗时和错误分类，修复后回放同一 case，避免只根据最终文本判断问题。

### Q20：如何从测试角度评估 Agent 评测？

**参考回答：**

先固定一次任务的输入、预期结果、运行轨迹、工具结果、RAG 来源和最终回答，再检查任务是否完成、工具是否调用正确、回答是否有来源、输出格式是否正确、高风险问题是否拦截、用户确认是否完整，以及家庭成员信息是否隔离。

Agent 评测本身不能修改答案、写业务状态或调用业务工具。测试要覆盖正常任务、工具异常、无来源、缺确认、跨成员串扰和错误评估，区分被测 Agent 失败与 Agent 评测误判。

### Q21：用大模型做 Agent 评测，怎么降低评测偏差？

**参考回答：**

不能把一个大模型的分数当成唯一结论。明确规则可以直接用程序判断，例如输出格式、工具调用、是否有用户确认；主观质量再由大模型辅助评分，并用人工标注样本做校准。

版本对比时可以隐藏模型来源、交换答案顺序、多次抽样，并统计与人工结果的一致性。如果评测模型和被测模型来自同一家，还要特别关注表达偏好带来的自我偏差。

### Q22：Agent 评测集怎么保证覆盖主要路径？测试数据可以由 AI 生成吗？

**参考回答：**

先按业务路径和风险类型建立测试矩阵，而不是随机攒问题。至少覆盖正常续方、复诊材料、用药提醒、高风险医疗请求、工具超时、错误参数、无检索结果、提示词注入和跨家庭成员串用。

AI 可以扩写表达方式和边界组合，但预期工具、预期来源和安全结果必须人工审核。上线后还要把真实 badcase 脱敏后加入回归集，防止测试集长期只覆盖理想输入。

### Q23：Agent 执行时间很长或中途失败，测试怎么做？

**参考回答：**

测试要分别注入模型超时、工具超时、网络中断、流式连接断开和进程重启。检查系统能否保留运行轨迹和最近的任务状态，恢复后是否重复调用工具、重复创建草稿，或者把失败状态当成成功。

同一个固定用例要能回放，随机输出要固定种子或改用结果范围断言。偶发失败不能只靠重跑掩盖，要记录失败阶段、外部依赖、耗时和重试次数，判断是测试不稳定还是系统不稳定。

### Q24：怎么区分业务 Agent 出错，还是 Agent 评测判断错了？

**参考回答：**

先看客观证据：工具参数和结果、RAG 来源、用户确认、输出格式和安全规则。如果客观证据已经错误，说明业务 Agent 有问题；如果客观证据正确，但评测结论与人工标准不一致，才考虑评测规则或评测模型有问题。

评测系统也要有自己的测试集，包含明确正确、明确错误和容易产生歧义的样本，并定期检查它与人工标注的一致性。

## 5. 测试开发面试自检

- 能否区分单元测试、集成测试、API/UI 测试和 E2E 测试？
- 能否解释 fixture、参数化、mock、monkeypatch 和测试数据隔离？
- 能否为图片、随机输出和大模型结果设计稳定评估？
- 能否说清测试报告、CI flaky、性能指标和失败诊断信息？
- 能否把测试结果和产品风险、回滚、监控联系起来？
- 是否避免把模型生成的测试用例直接当作正确答案？
